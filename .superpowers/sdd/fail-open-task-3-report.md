# Отчёт по этапу 3: достоверная диагностика ограниченной готовности

Дата проверки: 2026-08-06.

## Цель и граница

Этап 3 плана `2026-08-06-smart-runtime-fail-open.md` завершает диагностику,
установщик и пользовательскую документацию для двух разных состояний:

- `READY` — умная маршрутизация полностью доказана и доступна;
- `DEGRADED` — основной Codex доступен, но полная готовность умной части на
  текущей проверке не доказана.

Живая глобальная установка, десять циклов запуска и возобновления, публикация
и слияние относятся к этапу 4 и этим отчётом не подтверждаются.

## Разработка через RED и GREEN

Сначала отдельным коммитом `12fc6cb` добавлены проверки, которые фиксировали
отсутствующие требования:

- строгую схему снимка обновления координатора;
- атомарную публикацию снимка вместе с состоянием выбора;
- отклонение повреждённых расширений health вместо ложного `READY`;
- честный `DEGRADED` и диагностические поля установщика.

До реализации проверки падали из-за отсутствующих
`validate_coordinator_refresh_diagnostics_v2` и
`publish_coordinator_refresh`, принятия повреждённого расширения и выдачи
`HEALTH_ONLY`/`FULL_READY` вместо `DEGRADED`.

Рабочее исправление зафиксировано коммитом `d5efc0f`. Документация и её
проверки зафиксированы коммитами `89faf5c` и `2da5e6b`.

## Исправления по независимому ревью

Ревью выявило путь совместимости, который обходил новую атомарную публикацию:
`publish_coordinator_selection()` менял выбор, но сохранял старую диагностику
`SELECTED`. Поэтому один ответ health мог объединить новый выбор со старым
доказательством проверки, а `doctor` — ошибочно выдать `FULL_READY`.

Отдельный RED-коммит `a6450e7` воспроизвёл последовательность через старый
интерфейс. Проверка получила устаревшее расширение вместо ожидаемого пустого:

```text
Ran 1 test in 0.095s
FAILED (failures=1)
```

Коммит `0c8979b` сохранил старую сигнатуру и блокировку, но теперь публикация
выбора под той же блокировкой атомарно отзывает не связанное с ним
доказательство. Тот же сценарий после исправления:

```text
Ran 1 test in 0.098s
OK
```

Второе замечание касалось неизвестных полей health `extensions`. Исследование
схемы `controller-protocol-v2`, реестра отпечатков и описания жизненного цикла
подтвердило, что это намеренно открытая точка расширения: закрывать её до
единственного `coordinatorRefresh` нельзя без изменения договора
совместимости. Коммит `825111b` зафиксировал два свойства:

- ограниченное неизвестное расширение не меняет готовность, координатора или
  отпечаток шлюза и не сохраняется в решении;
- вложенный ключ `extensions`, более 128 узлов и размер более 16 КиБ должны
  отклоняться как несоответствие привязки контроллера.

До рабочей правки три варианта нарушения структурного бюджета ошибочно
оставались `READY`. После `0c8979b` они отклоняются, а безопасное неизвестное
расширение остаётся совместимым. Совместный повтор трёх новых сценариев:

```text
Ran 3 tests in 0.925s
OK
```

## Реализованное поведение

- Снимок диагностики имеет закрытый набор полей `status`, `reasonCode`,
  `lastSuccessfulCheckAt`, `nextAttemptAt` и строгие канонические отметки
  времени в UTC.
- Фоновая проверка использует интервалы 5, 30, 120 и 300 секунд; после успеха
  контрольная проверка выполняется через 300 секунд.
- Успешно доказанная проверка каталога обновляет `lastSuccessfulCheckAt`, даже
  если совместимая пара координатора не найдена. Тайм-аут это поле не
  обновляет.
- Публикация выбора и диагностики защищена общей блокировкой. Остановка
  фонового исполнителя дожидается завершения его нити.
- Совместимый старый интерфейс публикации выбора под той же блокировкой
  отзывает прежнюю диагностику, поэтому без свежего парного доказательства
  `FULL_READY` невозможен.
- Если подходящая пара ещё ни разу не была доказана, недоступность каталога
  оставляет умную часть недоступной. Если пара ранее была доказана, временная
  ошибка обновления сохраняет её для маршрутизации, но `doctor` честно
  сообщает `DEGRADED` и свежую причину, потому что актуальность каталога не
  доказана.
- Повреждённое или неполное расширение health не может дать ложный `READY`.
- Публичная причина `DEGRADED` берётся из `coordinatorReasonCode`, а не из
  общего `gatewayReason=READY`.
- `smoke` считается успешным только при полной готовности; доступность одного
  основного Codex не выдаётся за готовность умной маршрутизации.
- Центральная навигация, руководство эксплуатации, карта потока и описание
  дополнения показывают различия состояний, восстановление и поведение команд
  `codex` и `codex resume --last`.

## Проверки

Канонический полный целевой прогон выполнен в зафиксированном окружении
проекта:

```text
uv run --locked python -m unittest \
  tests.smart_subagents.test_coordinator_selection_v2 \
  tests.smart_subagents.test_controller_health_v2 \
  tests.smart_subagents.test_health_bootstrap_v2 \
  tests.smart_subagents.test_activation_gateway_v2 \
  tests.smart_subagents.test_install_adaptive_subagents \
  tests.smart_subagents.test_installer_command_v2 \
  tests.smart_subagents.test_protocol_v2_contract_vectors \
  tests.smart_subagents.test_docs_navigation

Ran 323 tests in 149.893s
OK
```

Первый запуск обычным `python3` дошёл до 301 проверки, но две проверки
окружения завершились ошибкой импорта `jsonschema`, которого нет в глобальном
Python. Это не было скрыто исправлением кода: повтор выполнен штатной командой
`uv run --locked`, указанной в `Makefile` и использующей зависимости из
`pyproject.toml`.

Дополнительные проверки:

```text
uv run --locked python -m py_compile <затронутые модули и установщик>
код возврата 0

uv run --locked python scripts/update_coordinator_contract_cascade.py --check
каскад договора координатора воспроизводим

uv run --locked python scripts/validate_docs_navigation.py
ok docs_navigation

git diff --check
код возврата 0
```

Закрытая схема `coordinatorSelection` не менялась: новые сведения передаются
через уже предусмотренный контейнер расширений health, поэтому обновление
каскада договорных артефактов не потребовалось.

## Изменённые области

- выбор координатора, health-сервер, начальная сборка health и шлюз активации;
- диагностика установщика;
- целевые модульные и документационные проверки;
- корневой README, руководство эксплуатации, карта потока и README
  дополнения.

## Остаточные риски

- Модульные и интеграционные проверки этапа 3 не заменяют живую приёмку уже
  установленной пользовательской конфигурации.
- Сохранение ранее доказанной пары после сбоя обновления намеренно допускает
  продолжение маршрутизации, но состояние остаётся `DEGRADED`, пока новая
  проверка каталога не докажет актуальность.
- Окончательное утверждение, что сообщения об остановленных обработчиках и
  требования `codex-native` исчезли во всех живых сценариях, возможно только
  после этапа 4 с повторной установкой и десятью циклами запуска/возобновления.
