# План реализации: спецификация наблюдателя вместимости Codex и безопасный режим диагностики

> **Для агентных исполнителей:** обязательно применять `superpowers:subagent-driven-development` (предпочтительно) или `superpowers:executing-plans`. Ход выполнения отмечать флажками `- [ ]`.

**Цель:** сделать договор ограничителя вместимости понятным и проверяемым, устранить смешение предела дочерних нитей с фактическим допуском машины и определить безопасные границы диагностического либо принудительного режима.

**Архитектура:** `codex_capacity_observer.py` остаётся единственным поставщиком живой оценки ресурсов, `codex_capacity.py prepare-wave` — единственным источником `allowed_wave_size`, а `codex_fd_doctor.sh` — совместимым входом для навыков. Новый договор должен отделять конфигурационный предел Codex, наблюдаемую вместимость машины, внешние процессы и доверие к широкой волне. Обычный запуск не получает обхода наблюдателя; возможный опасный запуск рассматривается только как отдельная, явно подтверждённая операторская функция.

**Технологии:** Python 3, zsh, JSON, SQLite, TOML, `unittest`, SHA-256.

## Глобальные ограничения

- Не включать hooks, смарт-запуск или скрытую автоматическую маршрутизацию.
- Не считать `agents.max_concurrent_threads_per_session` доказательством свободных ресурсов: это только верхняя граница одновременно открытых дочерних нитей Codex.
- Считать `allowed_wave_size=19` единственным допуском для плоского доверенного запуска `consilium` из 19 ролей.
- Число процессов `node_repl` само по себе не является причиной блокировки; блокировать можно только доказанную утечку, недостаток ресурсов либо недоступное обязательное измерение.
- Не завершать чужие процессы Codex, ChatGPT или `node_repl` автоматически. Любое завершение требует отдельного установления владельца и явного поручения.
- Тестовые переменные окружения и подставные снимки не могут использоваться как доказательство живого допуска и не должны открывать настоящий запуск.
- Все изменения пользовательского профиля, состояния и установленного контура выполнять через установщик с резервной копией и откатом.

## Подтверждённое исходное состояние

1. `scripts/codex_fd_doctor.sh` для доверенной волны передаёт манифест в `scripts/codex_capacity.py prepare-wave`.
2. `scripts/codex_capacity_observer.py` сохраняет защищённое состояние в `~/.local/state/codex-capacity-v1/observer_state.json`; красное состояние даёт нулевой допуск, жёлтое — максимум две роли, зелёное использует доказанную ступень вместимости.
3. После красного состояния требуются три нормальных снимка с интервалом 10 секунд; после жёлтого — 60 секунд нормального состояния.
4. До 30 принятых живых калибровочных скобок вместимость фиксирована на шести. Далее она может повышаться только ступенями `8 → 12 → 16 → 20` после десяти чистых насыщенных циклов на каждой ступени.
5. `external_codex_roots` вычитаются из допуска ровно один раз. Поэтому доказанная вместимость 20 при четырёх внешних корнях даёт не более 16 мест новой волны.
6. В текущем контуре нет поддерживаемого пользовательского ключа, который отключает наблюдателя только для живого запуска. Существующие режимы подстановки измерений ограничены испытаниями.

## Решения владельца, необходимые до опасного режима

До их явного выбора реализуются только задачи 1–4 и 6; задача 5 не начинается.

1. Нужен ли вообще запуск, обходящий живой допуск?
   - **Рекомендуется:** нет; добавить только режим чтения и объяснение причины отказа.
   - **Альтернатива:** отдельный операторский опасный режим с ограниченным сроком действия и неизменяемым журналом.
2. Если опасный режим нужен, какова его граница?
   - только имитация и проверка команды без создания ролей;
   - либо реальный запуск одной явно указанной волны с размером не более 19.
3. Кто подтверждает владение внешними корнями Codex перед их штатным завершением и где хранится это подтверждение?

## Риски и меры

| Риск | Влияние | Мера |
|---|---|---|
| Подмена живых измерений испытательными | Ложный допуск и потеря контроля | Жёстко разделить тестовый и рабочий путь; не считать тестовую ветвь приёмкой |
| Смешение внешних корней и помощников | Ложная блокировка либо переподписка ресурсов | Публиковать тип владения и применять вычет только один раз |
| Сброс файла состояния как обход | Потеря калибровки и непредсказуемое поведение | Запретить как метод допуска; чистое состояние остаётся на базовом пределе 6 |
| Неявный опасный режим | Запуск без понимания риска | Отдельный интерфейс, срок, журнал и подтверждение владельца |
| Долгая жёлтая или красная фаза | Непонятная остановка работы | Режим только чтения с точным `next_action` и показом восстановления |

До реализации задачи 5 владелец выбирает отсутствие опасного обхода либо его строго ограниченный операторский договор. После выбора задачи выполняются последовательно с независимой проверкой после каждой контрольной точки.
