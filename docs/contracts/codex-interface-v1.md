# Договор совместимости Codex `codex-interface-v1`

Статус: нормативная часть проекта решения от 17 июля 2026 года.

[Назад к проекту решения](../plans/2026-07-17-codex-capability-compatibility-idempotent-lifecycle-design.md)

[Машинные схемы договора](schemas/README.md)

## Назначение

Этот договор определяет, при каких наблюдаемых свойствах установленный Codex
можно использовать для адаптивного запуска субагентов. Номер выпуска остаётся
диагностическим фактом и нижней защитной границей, но не является списком
разрешённых версий. Совместимость доказывается на частном снимке конкретного
исполняемого файла.

Договор не доказывает происхождение произвольного файла и не обновляет Codex.
Текущая реализация поддерживает только `darwin-arm64` и подписанный выпуск
OpenAI. Для другой платформы или другого подписанта нужен новый именованный
адаптер источника; молчаливое ослабление проверки запрещено.

## Канонические данные и отпечатки

### Каноническая форма `canonical-json-v1`

Во всех собственных манифестах, свидетельствах, квитанциях и протоколах
применяется одна реализация `canonical-json-v1`:

1. допустимы только `null`, логические значения, строки, целые числа от
   `-(2^53-1)` до `2^53-1`, массивы и объекты;
2. вещественные числа, `NaN`, бесконечности, повторные ключи и непарные
   суррогаты Unicode запрещены;
3. ключ объекта является строкой и упорядочивается по возрастанию байтов его
   UTF-8-представления;
4. массив сохраняет порядок. Поле, объявленное множеством, до сериализации
   удаляет повторы и сортирует элементы по их собственному каноническому
   байтовому представлению;
5. целое число записывается десятичными знаками ASCII без плюса, ведущих нулей
   и формы `-0`;
6. кавычка и обратная косая черта строки экранируются как `\"` и `\\`;
   каждый знак U+0000–U+001F записывается строчной формой `\u00xx`; остальные
   скалярные значения Unicode пишутся непосредственно в UTF-8. Косая черта не
   экранируется, нормализация Unicode не выполняется;
7. между элементами нет пробелов, разделители равны `,` и `:`, завершающего
   перевода строки нет.

Исполняемая эталонная проверка реализует эти правила напрямую, без подмены
обычным сериализатором JSON. Положительные векторы побайтно закрепляют пять
управляющих знаков U+0008, U+0009, U+000A, U+000C, U+000D, кавычку, обратную
и обычную косую черту, обе безопасные целочисленные границы, порядок ключей
по UTF-8 и сохранение порядка массива. Отрицательные построения отдельно
отклоняют вещественное число, `NaN`, обе бесконечности, оба выхода за
безопасный целочисленный диапазон, оба непарных суррогата, кортеж, байтовую
строку и нестроковый ключ объекта.

Все машинные схемы и векторы до интерпретации читаются тем же строгим
входным слоем: повторный ключ, `NaN`, любая бесконечность, вещественное число,
целое вне безопасного диапазона и непарный суррогат отклоняют весь файл.
Повторные ключи нельзя сначала схлопнуть в обычный объект, а затем передать
каноническому кодировщику.

Отпечаток вычисляется так:

```text
SHA256(UTF8(domain) || 0x00 || canonical-json-v1(value))
```

## Частный снимок исполняемого файла

### Источник не является исполняемой границей доверия

Лексическую точку запуска задаёт оператор параметром `--codex-binary` либо
сохраняет манифест. Она может быть ссылкой Homebrew в каталоге, доступном
группе `brewadmins`. Такой путь считается только источником для копирования,
а не неизменяемым исполняемым файлом.

Все обходы назначения выполняются относительно заранее открытых дескрипторов
каталогов. Каждый компонент пути открывается через `openat` с
`O_DIRECTORY|O_NOFOLLOW|O_CLOEXEC`, проверяется через `fstat` и не разрешается
повторно по строке. Разрешённый при первичном выборе абсолютный путь источника
остаётся недоверенным: каталоги Homebrew могут принадлежать отдельному uid и
допускать запись группе `brewadmins`. Их владельцы и режимы не переносятся в
решение о доверии. Частные каталоги назначения принадлежат текущему
пользователю, имеют режим `0700` и не содержат жёстких связей на обычные файлы
с числом связей, отличным от одного.

Установщик:

1. сохраняет лексический абсолютный путь, разрешает цепочку ссылок только при
   первичном выборе источника, затем повторяет дескрипторный обход конечного
   пути и открывает обычный файл с `O_RDONLY|O_NOFOLLOW|O_CLOEXEC`;
2. проверяет обычный файл, ненулевой размер не более 1 ГиБ и возможность
   чтения из уже открытого дескриптора; uid и режим недоверенного источника не
   являются доказательством совместимости;
3. создаёт временный файл через `openat` с
   `O_WRONLY|O_CREAT|O_EXCL|O_NOFOLLOW|O_CLOEXEC`, режимом `0500` и числом
   жёстких связей один, потоково копирует в него открытый файловый дескриптор,
   одновременно вычисляя SHA-256;
4. синхронизирует файл, закрывает его и проверяет, что источник не изменил
   устройство, номер файла, размер и время изменения за время копирования;
5. доказывает формат `Mach-O 64-bit arm64` собственным разборщиком заголовка
   и единственную архитектуру `arm64` вызовом
   `[/usr/bin/lipo,-archs,SNAPSHOT]`; затем без оболочки выполняет точные
   вызовы `[/usr/bin/codesign,-v,--strict,--all-architectures,SNAPSHOT]` и
   `[/usr/bin/codesign,-v,--strict,--all-architectures,-R,REQUIREMENT_ARG,
   SNAPSHOT]`, где `REQUIREMENT_ARG` начинается с обязательного знака `=` и
   равен `=identifier "codex" and anchor apple
   generic and certificate
   1[field.1.2.840.113635.100.6.2.6] exists and certificate
   leaf[field.1.2.840.113635.100.6.1.13] exists and certificate
   leaf[subject.OU] = "2DC432GLL2"`. Начальный `=` передаёт выражение как
   исходный текст требования; без него `codesign` трактует аргумент как путь
   к файлу требования. Извлечённые `Identifier=codex`,
   `TeamIdentifier=2DC432GLL2` и `CDHash` сохраняются в свидетельстве, но
   конкретный `CDHash` политикой не закрепляется;
6. запускает из временной копии только пробы версии и интерфейса;
7. перед публикацией повторяет `fstat`, хеш, архитектуру и оба вызова подписи,
   затем публикует копию одним дескрипторным `renameat` как
   `codex-snapshots/<полный-sha256>/codex`, с каталогами `0700` и файлом
   `0500`, синхронизирует файл и каждый изменённый каталог и повторно открывает
   опубликованный путь с `O_NOFOLLOW` для итоговой сверки.

Если целевой снимок с тем же полным SHA-256 уже существует, он побайтно,
структурно и по подписи сверяется и повторно используется. Совпавшее имя при
несовпавшем содержимом является повреждением, а не поводом перезаписи.
Субагенты исполняют только опубликованный снимок. Изменение ссылки Homebrew не
может подменить уже допущенный дочерний процесс.

Обычный Codex продолжает запускаться из выбранной пользователем точки. Если
её содержимое перестало совпадать с `sourceObservedSha256`, оболочка выключает
умный маршрут до следующего `apply`, но не мешает обычному Codex и не ищет
другой файл самостоятельно.

## `InterfaceEvidence`

Свидетельство является строгим объектом; добавочные поля, кроме корневого
`extensions`, запрещены:

```text
{
  "schemaVersion": 1,
  "contractVersion": "codex-interface-v1",
  "subject": SubjectV1,
  "semantic": SemanticV1,
  "subjectFingerprint": sha256,
  "semanticFingerprint": sha256,
  "compatibilityFingerprint": sha256,
  "extensions"?: object
}
```

`SubjectV1` имеет ровно поля `snapshotSha256`, `snapshotPath`, `size`,
`mode`, `uid`, `device`, `inode`, `mtimeNs`, `version`, `platform`,
`architecture`, `signatureIdentifier`, `teamIdentifier`, `cdHash`,
`sourceLocator`, `sourceObservedSha256`. Пути — абсолютные строки до 4096
байт; версия — до 64 байт; платформа равна `darwin`, архитектура — `arm64`;
отпечатки имеют 64 строчных шестнадцатеричных знака, кроме 40-значного
`cdHash`; целые неотрицательны и входят в диапазон `canonical-json-v1`.
`mtimeNs` является точной десятичной строкой наносекунд без знака и ведущих
нулей, кроме единственного значения `0`: реальное значение `st_mtime_ns`
может превышать безопасный целочисленный диапазон канонического JSON.
`mode` содержит только биты `0o7777`. Лексический `sourceLocator` не
используется для запуска дочернего процесса.

`SemanticV1` содержит:

- `extensionRelease`, `contractVersion`, `platformAdapter="darwin-arm64-v1"`;
- отсортированные множества `commands`, `options`, `appServerMethods`;
- объект `machineSchemas`: для каждого имени строгой схемы хранит
  `{schemaId,schemaSha256}`; обязательны `interface-evidence-v1`,
  `account-evidence-v1`, `config-requirements-normalized-v1`,
  `config-requirements-vector-recipe-v1`, `child-profile-v1`,
  `routing-policy-v2`, `child-jsonl-v1`, `otel-logs-v1`, `boundary-result-v1`,
  `reader-result-v1`, `writer-result-v1`;
- для каждой записи `schemaSha256 = SHA256(точные исходные байты файла)`;
  доменное хеширование и канонизация JSON для этого поля не применяются;
- объект числовых `probeBudgets` и отсортированное множество точных
  `negativeProbeIds`;
- `arg0AdapterVersion="arg0-v1"`;
- `routingPolicyFingerprint`, `bundledCatalogFingerprint` и закрытую карту
  `childProfiles` с ровно тремя ключами `classifier`, `reader`, `writer`;
  значение каждого ключа является отпечатком соответствующего строгого
  `ChildProfileV1`.

Каждая строка и имя свойства семантики непусты и не превышают 256 байт;
множество содержит не более 256 элементов, карта схем — не более 32 записей.
Машинные схемы являются собственными строгими объектами с
`additionalProperties=false`; их `schemaSha256` вычисляется только из точных
исходных байтов файла обычным SHA-256.
Описательная документация, порядок вывода справки и динамический каталог
учётной среды в `SemanticV1` не входят.

`bundledCatalogFingerprint` строится из результата
`debug models --bundled`. Корень требует поле `models` — массив не более 256
объектов; добавочные описательные поля корня и модели игнорируются. Каждая
модель требует непустой уникальный `slug` до 128 байт и
`supported_reasoning_levels` — массив до 32 объектов с уникальным непустым
`effort` до 32 байт. Защитная проекция равна
`{"models":[{"model":slug,"reasoningEfforts":[...]}]}`; уровни и модели
сортируются по UTF-8, повторы запрещены. Отпечаток использует домен
встроенного каталога. Эта величина описывает подписанный снимок и не меняется
вместе с доступом учётной записи.
Положительный вектор содержит безопасную тестовую проекцию полного
встроенного каталога, её канонические байты и ожидаемый отпечаток; проверка
независимо сортирует модели и уровни по UTF-8, пересчитывает отпечаток доменом
`codex-smart/bundled-catalog/v1` и сравнивает его с `SemanticV1`.

Отпечатки строятся так:

- `semanticFingerprint` — домен семантики и объект `semantic` без
  `extensions`;
- `subjectFingerprint` — домен субъекта и объект `subject` без `extensions`;
- `compatibilityFingerprint` — домен совместимости и объект
  `{contractVersion,semanticFingerprint,subjectFingerprint}`.

Поле `extensions` и любые проигнорированные добавочные поля внешнего Codex не
могут выбирать модель, ослаблять профиль, менять результат совместимости,
влиять на переход состояния или входить в защитную проекцию. Отрицательная
проба изменяет такие поля и требует неизменности всех трёх отпечатков.

На диске кэшируется только `semantic` по ключу из полного SHA-256 снимка,
выпуска расширения, платформы, версии договора,
`routingPolicyFingerprint` и `bundledCatalogFingerprint`. `subject` всегда
строится заново из фактического снимка. Перед каждой умной сессией, перед
фиксацией допуска и ещё раз сторожем после кадра `COMMIT` непосредственно
перед `execve` повторяются дескрипторный обход, `fstat`, SHA-256, архитектура
и оба вызова подписи. Дочерний процесс запускается по частному пути снимка;
враждебные действия самого текущего пользователя и `root` остаются вне модели
угроз.

Поддерживаются только проверенные стабильные версии `0.144.4`, `0.144.5`,
`0.144.6` и `0.145.0`. Вывод обязан состоять из одной строки
`codex-cli MAJOR.MINOR.PATCH`. Суффикс предварительного выпуска, иной формат и
любая версия вне проверенного набора отклоняются адаптивным путём и передаются
обычному Codex.

## `AccountEvidence`

`AccountEvidence` имеет `schemaVersion=1`,
`contractVersion="codex-account-v1"` и содержит:

- закрытую копию `subject` с `snapshotPath`, `snapshotSha256` и
  `subjectFingerprint`, побайтно совпадающими с текущим `InterfaceEvidence`;
- канонический реальный путь `CODEX_HOME`, но не секреты из него;
- полный нормализованный результат `configRequirements/read`;
- полный набор пар `{model,reasoningEffort}` со всех страниц `model/list`;
- `requirementsFingerprint`, `accountCatalogFingerprint`,
  `accountContextFingerprint`, `recordFingerprint`;
- закрытый `collection` с постоянными корневыми ссылками, общими аргументами,
  полным несекретным окружением, пятью позиционными записями процессов и
  `collectionFingerprint`;
- ссылку на `compatibilityFingerprint`;
- время начала и окончания только как диагностические поля.

Диагностические `startedAt` и `finishedAt`, когда присутствуют, проверяются
как RFC 3339 через зарегистрированный формат JSON Schema `date-time`.
Отсутствующий обработчик формата считается ошибкой проверяющего окружения, а
не разрешением принять произвольную строку.

`requirementsFingerprint` охватывает нормализованное поле `requirements`.
`accountCatalogFingerprint` охватывает уникальный массив пар, отсортированный
сначала по UTF-8 модели, затем по UTF-8 уровня. `accountContextFingerprint`
охватывает объект `{codexHome,subjectFingerprint,compatibilityFingerprint,
requirementsFingerprint,accountCatalogFingerprint,collectionFingerprint}`.
`recordFingerprint` охватывает точный объект `{schemaVersion,contractVersion,
subjectFingerprint,compatibilityFingerprint,requirementsFingerprint,
accountCatalogFingerprint,accountContextFingerprint,collectionFingerprint}`,
но не времена и не `extensions`.
Внешний проверяющий модуль до вычисления `accountCatalogFingerprint` строит
эту сортированную проекцию и требует побайтного равенства входного массива с
ней. Перестановка пар отклоняется даже при корректном пересчёте каталога и
всей зависимой цепочки отпечатков.

Свидетельство не кэшируется между границами доверия. Каждая проверка выполняет
точную последовательность: `configRequirements/read A`, вся пагинация
`model/list A`, `configRequirements/read B`, вся пагинация `model/list B`,
`configRequirements/read C`. Каждый из пяти логических чтений использует
независимый процесс сервера приложения. Все страницы одного `model/list`
читаются в одном инициализированном процессе последовательными целыми
идентификаторами запросов. Все три нормализованных результата требований и
оба полных каталога обязаны попарно совпасть; курсор, повторённая страница,
повторённая модель с другим уровнем или изменение политики между чтениями
закрывают проверку. Общий срок одного `AccountEvidence` — 180 секунд; каждый
процесс, страница и чтение получает не свой новый срок, а остаток общего.

Все пять процессов запускаются только прямым `execve` точного
`subject.snapshotPath`; источник, ссылка Homebrew, `PATH` и повторное разрешение
пути для выбора исполняемого файла запрещены. `argv[0]` равен этому пути, а
оставшийся массив аргументов для каждого процесса побайтно равен
`["app-server","--strict-config","--listen","stdio://"]`.

`collection.rootReferences` является закрытым постоянным объектом:

```text
{
  "executablePath":"#/subject/snapshotPath",
  "subjectFingerprint":"#/subject/subjectFingerprint",
  "compatibilityFingerprint":"#/compatibilityFingerprint",
  "requirementsResult":"#/requirementsFingerprint",
  "catalogResult":"#/accountCatalogFingerprint"
}
```

Внешняя ссылка, иной указатель, цикл и разрешение через файловую систему
запрещены. `collection.argv` является точным массивом аргументов выше.
`collection.environment` не наследуется и является закрытой полной картой с
ровно семью ключами: `CODEX_HOME=codexHome`, `HOME`, `LANG=C`, `LC_ALL=C`,
`NO_COLOR=1`, `PATH=/usr/bin:/bin:/usr/sbin:/sbin`, `TMPDIR`. Секреты и
ссылки на секреты в ней запрещены. `environmentFingerprint` использует домен
окружения проверки учётной среды и всю эту карту.

Непосредственно перед каждым `execve` повторяются дескрипторный обход,
`fstat`, SHA-256, архитектура и обе проверки подписи; полученный
отпечаток обязан совпасть с разрешённым корневым `subjectFingerprint`, но
независимая копия этого значения в записи процесса не сохраняется. Закрытая
позиционная запись процесса содержит только порядковый номер, одно из точных имён
`requirements-a`, `catalog-a`, `requirements-b`, `catalog-b`,
`requirements-c`, точный `resultFingerprintRef` и `processFingerprint`.
Позиции 1, 3, 5 допускают только `#/requirementsFingerprint`, позиции 2, 4 —
только `#/accountCatalogFingerprint`.

Обязательный междокументный модуль `verify-account-evidence-v1` сначала
проверяет обе JSON Schema, сравнивает `subject` с текущим
`InterfaceEvidence`, разрешает только пять постоянных локальных указателей,
сверяет `CODEX_HOME`, а затем перед каждым процессом повторяет проверку
снимка. Для каждой позиции он строит точную проекцию
`{record,resolved,argv,environment,environmentFingerprint}`, где `record`
содержит три позиционных поля, а `resolved` — значения исполняемого пути,
субъекта, совместимости и результата, полученные только по корневым ссылкам.
`processFingerprint` использует домен процесса учётной среды и эту проекцию.
`collectionFingerprint` использует домен сбора и объект
`{processFingerprints:[...]}` в порядке пяти стадий. После этого модуль
пересчитывает `accountContextFingerprint` и `recordFingerprint`. Одна JSON
Schema проверяет форму и позицию, но не объявляется способом вычислять или
сравнивать криптографические значения. Поэтому независимую копию результата,
снимка или совместимости нельзя переставить в готовое свидетельство.
`smart_plan`, а также результаты `direct` и `clarify`, не запускают сбор
`AccountEvidence`. На этой стадии точная предлагаемая пара проверяется только
по отпечатанной политике и встроенному каталогу снимка. Она является частью
плана, но не разрешением запуска.

Для каждой фактически созданной попытки узла контроллер создаёт ровно одно
новое полное задание сбора. Оно связано с единственным `attemptId`, выполняет
ровно пять процессов в описанном порядке и завершается до подтверждения пары
по учётному каталогу и до выдачи допуска запуска. Кэш между попытками,
повторное использование результата предыдущего узла и скрытый повтор задания
запрещены. Повторная проверка неизменности снимка непосредственно перед
`execve` проверяет уже полученную запись и исполняемый файл, но не запускает
второй полный сбор. Новая полная проверка возможна только как новая явно
учтённая попытка.

Узел, допуск и фактическая попытка сохраняют один
`accountContextFingerprint`, полученный своим заданием. Если контекст меняется
после сбора и до `execve`, процесс не запускается, допуск становится
`ABORTED_ACCOUNT_CONTEXT_CHANGED`, а попытка завершается как `STALE`; уже
работающий процесс может только закончить аттестованную попытку, но её
результат не запускает зависимые узлы. Две учётные записи с одинаковыми
фактическими требованиями и парами моделей считаются эквивалентными. Пароли,
токены, электронный адрес и хеш файла авторизации не читаются и не
сохраняются.

Если полное свидетельство нельзя получить, завершается только соответствующая
попытка с `ACCOUNT_EVIDENCE_UNAVAILABLE`: допуск и дочерний процесс не
создаются. План остаётся наблюдаемым, но задание не ставится на скрытый повтор
и не переключается на другую модель. Следующий сбор требует новой попытки с
новыми `attemptId` и идентификатором задания.

## Нормализованная политика маршрутизации

Политика после разбора обязана пройти закрытую схему `routing-policy-v2`.
Неизвестное поле или значение блокирует умный маршрут. Отсутствующие в
исходной настройке значения материализуются до отпечатка точными значениями:
`hardFloor="none"`, `intervalPoint="max"`,
`unavailablePair="reject"`, `reassessment="promote-only"`. Защитная проекция
равна всему нормализованному объекту, а `routingPolicyFingerprint` вычисляется
доменом `codex-smart/routing-policy/v2`.

Смысловой вход имеет версию `q+p+v+o-v2` и замыкается пятью договорами:

Публичный `smart_plan` не принимает этот внутренний объект целиком. Узел
передаёт только `taskFacts` без разрешения делегирования, `contextBundle` и
`roleTemplateId`; публичный предел доказательств равен 63 и резервирует одну
запись для контроллера. Контроллер добавляет версии, фазу, ссылку на политику,
собственное разрешение, каталоги, сведения попытки и режим повторной оценки,
после чего полный `routing-input-v2` ровно один раз проверяется смысловым
маршрутизатором.

1. `task-facts-v1` хранит исходный текст, доказательства, форму работы,
   утверждения факторов и причины жёстких ограничений. Каждая известная
   величина и каждое доказанное утверждение ссылаются на существующий
   `evidenceRefId`; `false` без доказательства нормализуется в `unknown`, а
   недоказанное `true` отклоняется. Критерии `p` вычисляются только из четырёх
   счётчиков формы работы и не принимаются готовым выводом классификатора.
2. `delegation-policy-v2` сначала выдаёт одно из `clarify`, `direct`,
   `delegate`. Причина `clarify` старше причины `direct`; обе завершают выбор
   до вычисления модели. Только `delegate` переходит к выбору пары.
3. `role-template-v1` связывает смысловую роль с неизменяемым профилем
   исполнения: исследователь, диагност, проверяющий и аудитор рисков являются
   читающими, исполнитель — пишущим.
4. `context-bundle-v1` материализует передаваемый контекст, ограничивает его
   точным числом байтов и связывает каждый фрагмент с текущим доказательством.
   Изменившийся или исчезнувший источник делает ссылку устаревшей и блокирует
   запуск.
5. `routing-input-v2` различает фазы `smart-plan` и `node-attempt`. Первая не
   содержит задания `AccountEvidence` и учётного каталога; вторая содержит
   ровно одно полное задание на текущую попытку и фактический учётный каталог.

Историческая шкала версии 1 с шестью факторами
`ambiguity`, `dependencyDepth`, `breadth`, `novelty`, `harm`, `crossDomain`
остаётся отдельным интерфейсом совместимости. Её поля и формула не принимаются
как вход `q+p+v+o-v2`; смешение версий завершается
`SEMANTIC_VERSION_MISMATCH` до оценки.

Решение использует ровно четыре фактора `q`, `p`, `v`, `o`. Политика хранит
закрытые `factorDefinitions`, а результат классификатора — полную закрытую
карту `criterionStates` для всех известных идентификаторов. Состояние каждого
критерия равно `false`, `true`, `unknown` или `conflict`; пропуск до
нормализации означает `unknown`, неизвестный идентификатор блокирует маршрут.
Нормализованный `BoundaryResult` уже содержит все идентификаторы, поэтому
пропуск в нём является ошибкой схемы.

Критерии исчерпывающе делят ненулевые значения:

| Фактор | Значение 0 | Критерии 1 | Критерии 2 |
|---|---|---|---|
| `q`, зависимые рассуждения | ни один критерий 1/2 не доказан | цепочка не менее двух зависимых выводов; ограниченный выбор не менее чем из двух вариантов по двум ограничениям | инвариант через границы; состязательный контрпример для безопасности, доверия, конкурентности, атомарности, восстановления или отката; синтез конфликтующих доказательств |
| `p`, объём работы | не более одной адресуемой единицы, рабочей единицы, границы и ветви | от 2 до 5 адресуемых или рабочих единиц при одной границе и ветви | не менее 6 единиц, либо не менее 2 границ, либо не менее 2 независимых ветвей |
| `v`, цена ошибки | только чтение, совет или удаляемый временный результат без внешнего последствия | обратимое сохраняемое состояние; изолированное видимое изменение | общее или производственное состояние; разрушение либо недоказанный откат; доверие, секреты или права; критические последствия; выпуск или миграция |
| `o`, неопределённость | обязательные факты подтверждены, воспроизводимы и согласованы | факт достижим безопасным чтением; изменяемое текущее состояние; явная обратимая гипотеза | конфликт полномочий; недоступный обязательный факт или решение владельца; невоспроизводимый конфликт; незакреплённый интерфейс |

Адресуемая единица — отдельный файл, схема, страница, набор данных, результат
команды или выход; рабочая единица — независимо проверяемое изменение или
исследование; граница — репозиторий, независимо развёртываемый процесс,
внешний сервис или учётная среда; ветвь — независимая работа до общего
синтеза.

Для каждого фактора `min` равен максимуму из нуля и уровней критериев со
состоянием `true`. `max` равен максимуму из `min` и уровней критериев со
состоянием `true`, `unknown` или `conflict`. Выбирается `max`. Обязательный
нормализатор независимо пересчитывает интервалы `q`, `p`, `v`, `o` из
`criterionStates` и отклоняет рассогласование. Каждый выбранный фактор
принадлежит `0..2`; оценка равна точной сумме `score=q+p+v+o` и принадлежит
`0..8`. Схема допускает только `0<=min<=max<=2`.

Исполняемые векторы содержат отдельное состояние `conflict` ненулевого уровня
для каждого из `q`, `p`, `v`, `o`; во всех четырёх случаях нижняя граница
остаётся нулевой, а верхняя принимает уровень конфликтующего критерия.
Удаление `conflict` из `upperStates` обязано изменить результат каждого из
четырёх векторов. Два полных `BoundaryResult` используют одинаковые состояния:
с интервалом `q={min:0,max:1}` результат согласован, а с
`q={min:0,max:0}` проходит схему, но отклоняется проверкой политики. При
искусственном удалении `conflict` из `upperStates` исходы обеих проверок
меняются на противоположные.

Таблица выбора закрыта:

| Оценка | Ступень | Модель | Уровень рассуждения |
|---:|---|---|---|
| `0` | Luna | `gpt-5.6-luna` | `low` |
| `1` | Luna | `gpt-5.6-luna` | `low` |
| `2` | Luna | `gpt-5.6-luna` | `medium` |
| `3` | Terra | `gpt-5.6-terra` | `medium` |
| `4` | Terra | `gpt-5.6-terra` | `medium` |
| `5` | Terra | `gpt-5.6-terra` | `high` |
| `6` | Sol | `gpt-5.6-sol` | `high` |
| `7` | Sol | `gpt-5.6-sol` | `xhigh` |
| `8` | Sol | `gpt-5.6-sol` | `max` |

Жёсткий нижний предел имеет закрытые значения `none`, `terra`, `sol` и
пересчитывается из полного множества `hardFloorReasons`. Terra требуется для
безопасности, архитектурного решения, публичного договора или рискованной
миграции. Sol требуется для необратимого действия, недоказанного отката,
критического сбоя или окончательной авторской проверки перед публикацией.
Берётся старший сработавший предел; неизвестная причина и рассогласование
готового `hardFloor` с причинами блокируют маршрут.
`terra` повышает младшую ступень как минимум до пары
`gpt-5.6-terra + medium`, `sol` — до `gpt-5.6-sol + high`; `none` не повышает
табличный выбор. При повышении ступени усилие равно большему из табличного
усилия и минимального усилия новой ступени в порядке
`low < medium < high < xhigh < max`.

`allowedPairs` в отпечатанной политике содержит семь атомарных пар, выбранных
таблицей. Для `smart-plan` выбранная точная пара как единый объект обязана
присутствовать в `policyPairs` и `bundledSnapshotPairs`. Для фактической
`node-attempt` та же пара дополнительно обязана присутствовать в
`accountPairs`, полученном единственным полным заданием этой попытки. Модель из
одной записи и уровень из другой не соединяются. Если точной пары нет хотя бы
в обязательном для текущей фазы источнике, результат равен
`ROUTING_PAIR_UNAVAILABLE`: похожая модель, соседнее усилие, понижение и
скрытый повтор запрещены.

Перед повторной оценкой попытки проверяются неизменность отпечатков политики,
встроенного каталога и свежего учётного каталога, а также наличие текущей пары
во всех трёх массивах. Изменение отпечатка или исчезновение текущей пары даёт
`STALE`, даже если более сильный кандидат доступен. После этого кандидат
строится тем же алгоритмом и сравнивается с текущей парой по номеру ступени,
затем по порядку усилий. Итог равен большему из текущей пары и кандидата;
недоступный повышенный кандидат завершает допуск
`ROUTING_PAIR_UNAVAILABLE`, а не сохраняет молча старую пару.
`hardBan=direct` исключает дочерний запуск, `hardBan=clarify` требует
уточнения; эти значения не являются модельными ступенями.

## Командная поверхность

Справка разбирается структурно по именам команд и параметров. Полный текст и
порядок пояснений не сравниваются. Противоречащие формы одного параметра или
неразбираемый раздел означают несовместимость.

| Поверхность | Обязательная форма |
|---|---|
| Версия | `codex --version`, одна строка указанного формата |
| Корень | `codex --help`; команды `app-server`, `debug`, `exec`, `plugin`, `sandbox`; весь найденный набор верхних команд передаётся обычному Codex без умной классификации |
| Исполнение | `codex exec --help`; `--ignore-user-config`, `--ignore-rules`, `--strict-config`, `--ephemeral`, `--json`, `--skip-git-repo-check`, `--model`, `-C` или `--cd`, `--output-schema`, `-c` или `--config`, `--disable` |
| Сервер приложения | `codex app-server --help`; `--strict-config`, `--listen`; форма запуска `app-server --strict-config --listen stdio://` |
| Встроенные модели | `codex debug models --bundled`; строка имеет непустой `slug` и массив `supported_reasoning_levels` из уникальных объектов с непустым `effort` |
| Песочница | `codex sandbox --help`; `-P`, `--include-managed-config`, `-C`, `-c`, разделитель `--` |
| Подключаемые модули | формы `plugin list --json`, `plugin add ID --json`, `plugin remove ID --json`, `plugin marketplace list --json`, `plugin marketplace add PATH --json`, `plugin marketplace remove NAME --json` присутствуют в дереве справки |

Дочерний вызов задаёт `approval_policy="never"`, пустые
`project_root_markers`, `project_doc_max_bytes=0`, наследование окружения
`none`, закрытый набор переменных, `allow_login_shell=false`,
`agents.max_threads=1`, `agents.max_depth=1` и `web_search="disabled"`.

Для всех ролей обязательно отключены:

```text
apps browser_use browser_use_external browser_use_full_cdp_access
computer_use enable_fanout enable_mcp_apps hooks in_app_browser memories
multi_agent multi_agent_v2 plugins remote_plugin shell_snapshot
skill_mcp_dependency_install workspace_dependencies
```

Классификатор дополнительно отключает:

```text
auth_elicitation code_mode_host goals image_generation
request_permissions_tool shell_tool tool_call_mcp_elicitation
tool_suggest unified_exec
```

`ChildProfileV1` является одним из трёх полных постоянных вариантов схемы
`child-profile-v1`: `classifier`, `reader`, `writer`. Для каждой роли машинно
закреплены весь объект, точный порядок и состав `argvTemplate`,
`environmentTemplate`, `disabledFeatures` и `negativeProbeIds`. Произвольный
литерал, перестановка, удаление или добавление элемента недопустимы. Отпечаток
использует домен профиля дочернего процесса и весь постоянный вариант;
фактические пути, модель, усилие, рабочий каталог, окружение и секрет в него
не входят.

Элемент `argvTemplate` является ровно одним из `{literal}` или
`{slot,prefix,encoding}`. Разрешены и встречаются ровно по одному именованные
места `snapshotPath`, `model`, `workDir`, `resultSchemaPath`,
`reasoningEffort`, `shellEnvironmentSet`. Подстановка сначала кодирует значение
указанным `raw`, `json-string` или `toml-inline-table`, затем добавляет точный
`prefix`; отсутствие, повтор или неизвестное место блокирует запуск. Общий
префикс после подстановки равен:

```text
SNAPSHOT exec --ignore-user-config --ignore-rules --strict-config
--ephemeral --json --skip-git-repo-check --model MODEL
-C WORK_DIR --output-schema SCHEMA
-c model_reasoning_effort=JSON_EFFORT
-c approval_policy="never"
-c default_permissions=JSON_PROFILE
-c project_root_markers=[]
-c project_doc_max_bytes=0
-c shell_environment_policy.inherit="none"
-c shell_environment_policy.set={...}
-c allow_login_shell=false
-c agents.max_threads=1
-c agents.max_depth=1
-c web_search="disabled"
```

После шаблона следуют пары `--disable FEATURE` в точном порядке массива
`disabledFeatures`; иных аргументов нет. Никакое значение из подсказки или
ответа модели не добавляется в аргументы. Перед запуском проверяющий модуль
разрешает ожидаемый отпечаток только как
`InterfaceEvidence.semantic.childProfiles[role]`, загружает совпавший точный
вариант, подставляет пять динамических аргументов, строит
`shellEnvironmentSet`, добавляет отключения и побайтно сравнивает весь
конкретный массив. Независимая пара «роль + переданный отпечаток профиля» не
принимается.

Внешнее окружение процесса состоит ровно из `CODEX_ADAPTIVE_CHILD`,
`CODEX_ADAPTIVE_SNAPSHOT_ROOT`, `CODEX_HOME`,
`CODEX_SQLITE_HOME`, `HOME`, `LANG=C`, `LC_ALL=C`, `NO_COLOR=1`,
`PATH=/usr/bin:/bin:/usr/sbin:/sbin`, `TMPDIR`,
`OTEL_EXPORTER_OTLP_ENDPOINT`, `OTEL_EXPORTER_OTLP_HEADERS`; пишущая роль
дополнительно имеет `CODEX_ADAPTIVE_WORKSPACE_ROOT`. Значение заголовка является
одноразовым секретом. `nonSecretEnvironment` в привязке запуска является
закрытой картой всех перечисленных значений, кроме
`OTEL_EXPORTER_OTLP_HEADERS`; добавочный ключ запрещён. Значение места
`shellEnvironmentSet` получается только как детерминированная встроенная
таблица TOML: ключи сортируются, а строки кодируются как строки JSON, совместимые
с базовыми строками TOML. Заголовок телеметрии и любое секретное значение в
аргумент попасть не могут. Наследование остальных переменных отсутствует.

Конкретный запуск образует отдельный закрытый `ChildLaunchBindingV1` с ролью,
`compatibilityFingerprint`, пятью динамическими аргументами, конкретным
массивом `argv`, закрытым `nonSecretEnvironment`, `argvFingerprint`,
`environmentFingerprint`, `secretSha256`. Поле `profileFingerprint` и любое
поле с исходным секретом запрещены. `argvFingerprint` вычисляется доменом
`codex-smart/argv/v2` от точного конкретного массива `argv`.
`secretSha256` равен
`SHA256(UTF8("codex-smart/launch-secret/v1") || 0x00 || UTF8(secret))`.
`environmentFingerprint` использует домен `codex-smart/environment/v1` и
проекцию `{variables:NON_SECRET_ENV,secretBindings:
{OTEL_EXPORTER_OTLP_HEADERS:secretSha256}}`. Сам секрет, его длина и исходные
байты не сохраняются ни в профиле, ни в привязке, ни в журнале. Изменение
динамического значения не меняет ожидаемый отпечаток профиля в
`InterfaceEvidence`, но обязано менять соответствующий отпечаток конкретного
запуска.

Непосредственно перед запуском привязка проверяется вместе с отдельным
закрытым `TrustedLaunchContextV1`, содержащим все и только следующие поля:
`schemaVersion=1`, `contractVersion="codex-trusted-launch-context-v1"`, `role`,
`compatibilityFingerprint`, атомарную `selectedPair={model,reasoningEffort}`,
`resultSchemaPath`, `workDir`, `environmentSlotValues` и
`secretSlotFingerprints`. Вложенный `environmentSlotValues` также закрыт:
для ролей `classifier` и `reader` он содержит все и только слоты
`snapshotRoot`, `codexHome`, `codexSqliteHome`, `home`, `tmpDir`,
`otelEndpoint`, а для роли `writer` — те же слоты и дополнительно
`workspaceRoot`. Вложенный `secretSlotFingerprints` закрыт и для каждой роли
содержит все и только один слот `otelHeaders`. Путь снимка берётся только из
`InterfaceEvidence.subject.snapshotPath`; профиль и `resultSchemaId` — только
из роли и `InterfaceEvidence.semantic.childProfiles`; ожидаемый SHA-256 схемы
результата — только из соответствующей записи
`InterfaceEvidence.semantic.machineSchemas`. Проверяющий модуль сначала
проверяет обе схемы, совпадение роли и трёх отпечатков совместимости, затем
разрешает профиль, сравнивает выбранную пару как единый объект, хеширует
фактические исходные байты файла схемы результата обычным SHA-256 и сверяет
пять аргументов привязки: `snapshotPath`, `model`, `reasoningEffort`,
`resultSchemaPath`, `workDir`. После этого он заново материализует весь `argv`
из доверенных значений и пересчитывает `argvFingerprint`.

Виртуальный путь результата разрешается только по закрытой машинной записи
`resultSchemaResolution={virtualRoot:"/private/schemas",repositoryRoot:
"docs/contracts/schemas"}` из вектора дочерних профилей. Проверяющий модуль
требует точное имя `${resultSchemaId}.schema.json` непосредственно под обоими
корнями, запрещает выход из доверенного каталога, разрешает фактический путь
относительно переданного корня набора договоров и требует существующий обычный
файл. SHA-256 считается из байтов именно этого разрешённого фактического файла;
подмена записи разрешения, логического пути или отсутствие фактической цели
дают отказ.

Пять отрицательных векторов по одному меняют каждый динамический аргумент,
заново материализуют согласованный с ним `argv` и пересчитывают его отпечаток.
Такая привязка сама по себе остаётся допустимой по схеме и внутренне
согласованной, но совместная проверка с неизменным доверенным контекстом
обязана её отклонить. Для варианта пути схемы подготовлены два логических пути
к одинаковым исходным байтам, поэтому отказ доказывает именно несовпадение
пути, а не различие содержимого.

Для воспроизводимой проверки вектор содержит отдельно от привязок
`concreteLaunch.positiveRoles.*.binding` только
явную строку `syntheticSecretUtf8`, помеченную как тестовую и
непроизводственную. Проверка хеширует её исходные UTF-8 байты без кавычек
канонического JSON и сравнивает результат с `secretSha256`; в самой привязке
исходной строки нет.

Читающий профиль разрешает чтение только снимка репозитория и частного
временного дерева; пишущий добавляет запись только в отдельную карантинную
рабочую копию. Профили, полный массив аргументов, карта окружения без секрета
заголовка и именованные отрицательные пробы входят в
`childProfileFingerprint`. Пробы обязаны доказать: запрет записи читающим,
запрет записи вне карантина пишущим, отсутствие прямой сети и оболочки входа,
глубину и число субагентов один, невозможность включить отключённую
возможность из подсказки, отказ неизвестной строгой настройки и отсутствие
изменений исходного репозитория после каждой роли.

Исчезновение параметра, отказ строгой настройки либо неожиданно успешная
отрицательная проба означает несовместимость.

## Сервер приложения

### Транспорт и общий конверт

Одна логическая проба использует отдельный процесс, UTF-8 JSON по одной строке
и такую последовательность:

1. `initialize` с `id=1`, непустыми строками
   `clientInfo.{name,title,version}` и массивом
   `capabilities.optOutNotificationMethods`, содержащим
   `remoteControl/status/changed`;
2. ответ с тем же целым `id`, ровно одним из `result` или `error`;
3. уведомление `initialized` с пустым объектом `params`;
4. один или несколько запросов с возрастающими без пропусков целыми `id`,
   начиная с 2;
5. для каждого — ровно один ответ с тем же `id` и ровно одним из `result` или
   `error`.

Пагинация одного `model/list` целиком проходит в одном таком процессе; между
страницами новый `initialize` не выполняется. Два прохода каталога и три
чтения требований являются пятью независимыми логическими пробами и не
разделяют процесс или состояние.

Успешный `initialize.result` требует непустые строки `userAgent`, `codexHome`,
`platformFamily`, `platformOs`; реальный `codexHome` должен совпасть с
ожидаемым. Добавочные поля результата допускаются и игнорируются.

Ответ `error` должен быть объектом с непустым строковым `message` и полем
`code`, являющимся строкой или целым числом; `data` необязательно и только
ограниченно сохраняется для диагностики. Любая ошибка обязательного метода
делает соответствующую пробу неуспешной. Подмена ошибочного метода запасным
методом запрещена.

Парсер запрещает повторные ключи, вещественный или нецелый `id`, ответ на
неизвестный или уже завершённый `id`, два ответа на один запрос и более 128
неответных сообщений. До нужного ответа разрешены только уведомления с
объектом `params`, строковым `method` до 256 байт и без `id`; они учитываются
в общем размере, но не изменяют защитную проекцию. Серверный запрос с `id`,
неизвестная форма сообщения, уведомление после итогового ответа или закрытие
потока с незавершённым запросом делают пробу неуспешной.

У всех внешних результатов добавочные поля объекта разрешены и игнорируются,
если ниже не сказано обратное. Неизвестное значение защитного перечисления
блокирует умный режим. Это правило обеспечивает добавочную совместимость без
молчаливого принятия нового смысла.

### `model/list`

Параметры первой страницы равны
`{"includeHidden":true,"limit":100}`; следующая добавляет непустой `cursor`.
Не более 8 страниц, 100 строк на страницу, 800 строк всего; курсор не длиннее
4096 байт и не повторяется.

Результат требует массив `data` и необязательный `nextCursor`. Строка требует
непустой `model` до 128 байт и массив до 32 уникальных
`supportedReasoningEfforts`; его элемент требует непустой
`reasoningEffort` до 32 байт. Повтор модели на любой странице запрещён.
Добавочные поля результата, строки и уровня игнорируются. Поля `slug`,
`supported_reasoning_levels` и `effort` относятся только к встроенному
каталогу и не принимаются вместо формы сервера приложения.

### `configRequirements/read`

Параметры равны `{}`. Результат обязан содержать `requirements`, равный
объекту или `null`; отсутствие поля является
`MANAGED_REQUIREMENT_MALFORMED`. Добавочные поля рядом с `requirements`
игнорируются. Сгенерированная Codex схема является источником имён, но не
границей доверия: в ней почти нет пределов и запрета добавочных полей.
Локальная схема `config-requirements-normalized-v1` закрывает все структурные
объекты и знает ровно 16 полей:

| Поле | Тип до нормализации |
|---|---|
| `allowAppshots`, `allowManagedHooksOnly`, `allowRemoteControl` | `boolean \| null` |
| `allowedApprovalPolicies` | массив `"untrusted"`, `"on-request"`, `"never"` или строгого объекта `granular` |
| `allowedApprovalsReviewers` | массив `user`, `auto_review`, `guardian_subagent` |
| `allowedPermissionProfiles` | карта `непустая строка → boolean` |
| `allowedSandboxModes` | массив `read-only`, `workspace-write`, `danger-full-access` |
| `allowedWebSearchModes` | массив `disabled`, `cached`, `indexed`, `live` |
| `allowedWindowsSandboxImplementations` | массив `elevated`, `unelevated` |
| `computerUse` | объект с необязательным `allowLockedComputerUse: boolean \| null` |
| `defaultPermissions` | `string \| null` |
| `enforceResidency` | `"us" \| null` |
| `featureRequirements` | карта `непустое имя возможности → boolean` |
| `hooks` | `ManagedHooksRequirements \| null` |
| `models` | `{newThread?: {model?,modelReasoningEffort?,serviceTier?} \| null} \| null` |
| `network` | `NetworkRequirements \| null` |

Строгий `granular` содержит обязательные логические `mcp_elicitations`,
`rules`, `sandbox_approval` и необязательные `request_permissions`,
`skill_approval`; отсутствующие два последних и явный `null` нормализуются в `false`.
Эта материализация выполняется до дедупликации
`allowedApprovalPolicies`, поэтому отсутствующее значение, `null` и явный
`false` задают одну политику.
`ManagedHooksRequirements` требует все десять массивов
`PermissionRequest`, `PostCompact`, `PostToolUse`, `PreCompact`, `PreToolUse`,
`SessionStart`, `Stop`, `SubagentStart`, `SubagentStop`, `UserPromptSubmit` и
необязательные строки `managedDir`, `windowsManagedDir`. Группа содержит
`hooks` и необязательный `matcher`; обработчик имеет одну из закрытых форм:
`{type:"command",async,command,commandWindows?,statusMessage?,timeoutSec?}`,
`{type:"prompt"}` или `{type:"agent"}`.

`NetworkRequirements` знает только `allowLocalBinding`, `allowUnixSockets`,
`allowUpstreamProxy`, `allowedDomains`, `dangerouslyAllowAllUnixSockets`,
`dangerouslyAllowNonLoopbackProxy`, `deniedDomains`, `domains`, `enabled`,
`httpPort`, `managedAllowedDomainsOnly`, `socksPort`, `unixSockets`.
Логические поля допускают `null`; порты — `null` или целые `0..65535`;
устаревшие массивы содержат строки; карты `domains` и `unixSockets` имеют
значения `allow` или `deny`. Если одновременно даны каноническая и устаревшая
формы, их отсортированные разрешения и запреты обязаны совпасть.

Нормализация выполняется до отпечатка:

1. `requirements=null` сохраняется и отличается от пустого объекта;
2. внутри объекта отсутствующее необязательное поле и явный `null`
   эквивалентны и удаляются, а пустая коллекция сохраняется;
3. разрешительные массивы, кроме упорядоченных групп и обработчиков хуков,
   являются множествами: повторы удаляются, элементы сортируются по
   `canonical-json-v1`; порядок хуков сохраняется;
4. карты сортируются общим кодировщиком; Unicode не нормализуется;
5. неизвестное структурное поле на любой глубине даёт
   `MANAGED_REQUIREMENT_UNSUPPORTED`, неизвестное перечисление или неверный
   тип — `MANAGED_REQUIREMENT_MALFORMED`;
6. вся сырая оболочка и нормализованное дерево независимо ограничены 1 МиБ,
   глубиной 16 и 4096 узлами. Для разобранного входа `parsed` размером служит
   длина UTF-8 представления `canonical-json-v1` всей проверенной оболочки;
   размер текстового входа равен числу исходных байтов UTF-8 `raw-utf8`.
   Итеративная проверка типа, числа узлов и глубины выполняется до рекурсивного
   копирования, канонизации или нормализации пользовательского дерева и
   прекращается при первом доказанном превышении. Циклическая ссылка контейнера
   в `parsed` даёт `MANAGED_REQUIREMENT_MALFORMED`. Повторные ключи JSON запрещены;
   `timeoutSec` ограничен диапазоном целого `canonical-json-v1`. Предел мощности
   произвольных строковых множеств и карт остаётся равным 2048 элементам или
   свойствам. `maxLength` JSON Schema считает знаки Unicode;
   внешний проверяющий модуль отдельно считает байты UTF-8 и применяет те же
   договорные байтовые пределы к строкам.

Пять конечных разрешительных массивов `allowedApprovalPolicies`,
`allowedApprovalsReviewers`, `allowedSandboxModes`, `allowedWebSearchModes` и
`allowedWindowsSandboxImplementations` образуют закрытые множества.
Они не имеют отдельного преднормализационного предела 2048. Каждый исходный
элемент сначала проверяется
по закрытому типу и перечислению, затем повторы удаляются и результат сортируется
по `canonical-json-v1`; общие пределы 1 МиБ, 4096 узлов и глубины 16 действуют
до этой нормализации.

Смысловая проверка сравнивает требования с сохранённой в `SemanticV1`
проекцией фактического дочернего профиля. Для классификатора и читающего узла
это `read-only`, для пишущего — `workspace-write`; у всех
`approvalPolicy=never`, `webSearchMode=disabled`, хуки, приложения, удалённое
управление, использование компьютера и прикладная сеть выключены, а профиль
прав указан явно. Правила совместимости закрыты:

- заданные списки должны содержать `never`, фактический режим песочницы,
  `disabled` и выбранный профиль со значением `true`;
- `defaultPermissions`, если задан, обязан совпасть с явным профилем;
- каждое имя `featureRequirements` должно быть известно и его значение
  совпадает с доказанным фактическим значением;
- непустые `models.newThread.model` и `modelReasoningEffort` совпадают с
  выбранной парой; непустой `serviceTier` и любое `enforceResidency`
  блокируются, пока профиль не умеет их аттестовать;
- непустые управляемые хуки несовместимы с отключёнными дочерними хуками;
- `network.enabled=true`, ненулевые порты или требование включить привязку,
  прокси либо опасный сокет несовместимы с выключенной сетью;
- разрешающее логическое поле не заставляет включать выключенную возможность,
  но запрещающее поле обязательно ограничивает включённую;
- неизвестное имя возможности или новый защитный смысл дают
  `MANAGED_REQUIREMENT_UNSUPPORTED`, несовпадение известного ограничения —
  `MANAGED_REQUIREMENT_INCOMPATIBLE`.

Машинные векторы охватывают как минимум: `null`, отсутствующий корень,
эквивалентность отсутствия и `null`, различие `null` и `{}`, пустые списки,
читающий и пишущий профили, несовпадение одобрения, песочницы, поиска, профиля,
модели и уровня, неизвестную возможность, непустые хуки, конфликт двух форм
сети, неизвестное поле/перечисление, повторный ключ и каждый предел. Для
положительных векторов закрепляются точные канонические байты и SHA-256
домена управляемых требований.
Все 22 основных случая имеют непустые уникальные имена; последующие проверки
адресуют их по `name` и не допускают схлопывания разных случаев.

Точный набор предельных рецептов проходит закрытую схему
`config-requirements-vector-recipe-v1`. Каждый рецепт закрепляет `kind`,
полный `seed`, `targetPointer`, единственный `mutableParameter`, значения
`atLimit` и `overLimit`, оба ожидаемых результата и SHA-256 двух фактически
сгенерированных байтовых последовательностей. Схема фиксирует весь
утверждённый набор как постоянный объект, поэтому несовместимая комбинация
оператора, параметра, исходных данных или ожидания недопустима.

Исполнитель рецептов не имеет неявных случайных данных:

- `replace-integer` заменяет только целое по указателю;
- `replace-ascii-string` повторяет `a`, а `replace-utf8-string` повторяет
  двухбайтовое `é` и при нечётной цели добавляет одно `a`;
- `rename-single-property` сохраняет единственное значение и заменяет только
  имя ключом из `a`; `replace-map-value` меняет только значение;
- `populate-indexed-array` строит строки `item-NNNN`, а
  `populate-indexed-object` — ключи `kNNNN`; вариант двух карт сначала
  заполняет 2048 ключей `pNNNN`, затем оставшиеся `fNNNN`;
- рецепты групп и обработчиков добавляют точные `{"hooks":[]}` и
  `{"type":"prompt"}`;
- `append-raw-spaces` дополняет валидный исходный JSON пробелами,
  `solve-canonical-padding` распределяет `a` по командам по порядку без
  превышения 65536 знаков;
- `populate-raw-nodes` добавляет `null`, а `wrap-depth` оборачивает целевое
  значение объектами `{"x":...}`;
- `append-array-value` применяется отдельно к известному значению, повтору и
  неизвестному значению. Для случая удаления повтора сначала строится
  `atLimit`, затем повтор добавляется к нему для `overLimit`;
  нормализатор канонически сортирует уникальные элементы, и оба
  нормализованных результата должны быть побайтно равны.

Рецепты покрывают нижние и верхние границы портов и безопасных целых, пустую
и предельную строку, команду, многобайтовую строку, длину имени и допустимость
значения карты, мощности 2048, группы и обработчики 256, исходный и
канонический размер 1 МиБ, 4096 узлов и глубину 16. Валидная глубина 16
проходит общий ограничитель, но неизвестная структура затем отдельно даёт
`MANAGED_REQUIREMENT_UNSUPPORTED`; глубина 17 блокируется ограничителем как
`MANAGED_REQUIREMENT_MALFORMED`.

Пять конечных массивов с `uniqueItems` не имеют искусственного `maxItems`:
естественный максимум задаётся конечным перечислением. Полный известный набор,
добавленный повтор и неизвестное значение являются тремя отдельными случаями;
повтор удаляется нормализацией, неизвестное значение даёт
`MANAGED_REQUIREMENT_MALFORMED`. Вектор с повторным ключом объекта хранит
именно `inputRawUtf8` и передаётся строгому разборщику как исходные байты, а
не как уже разобранный объект.

### `hooks/list`

Параметры равны `{"cwds":[SYNTHETIC_CWD]}`. Результат требует массив `data`
из одного объекта с полями `cwd`, `errors`, `warnings`, `hooks`. `cwd`
совпадает с синтетическим каталогом. `warnings` является массивом строк.
`errors` является массивом закрытых объектов с ровно обязательными строками
`message` и `path`; добавочное поле, пустая или превышающая 4096 байт строка
делает пробу неуспешной. Непустой `errors` запрещает готовность.

Для целевого `pluginId` должны существовать ровно по одному включённому хуку
`userPromptSubmit` и `stop`. Каждый требует поля `currentHash`, `enabled`,
`eventName`, `handlerType`, `isManaged`, `key`, `pluginId`, `source`,
`sourcePath`, `timeoutSec`, `trustStatus`; `handlerType=command`,
`source=plugin`. Известны `managed`, `untrusted`, `trusted`, `modified`; готовы
только `managed` и `trusted`. Добавочные поля внешнего объекта игнорируются,
неизвестное состояние доверия запрещает готовность.

Все строковые поля непусты и не длиннее 4096 байт, `timeoutSec` — целое
`0..3600`, логические поля имеют настоящий JSON-тип. `sourcePath` является
абсолютным обычным файлом внутри выбранной активации, открывается с
`O_NOFOLLOW`, имеет владельца, режим, файловый идентификатор и SHA-256 из
`artifacts`. Для пары событий активация отдельно хранит ожидаемые
`{eventName,key,sourcePath,currentHash}`; фактические значения обязаны
побайтно совпасть. Любой третий целевой хук, повтор события, иной путь, хеш,
ключ, версия или источник закрывает готовность. Хуки других подключаемых
модулей не изменяются и не входят в доказательство владения этой активацией.

### Реестр подключаемых модулей

`plugin marketplace list --json` требует корневой массив `marketplaces`.
Целевой элемент требует непустые `name`, `root` и объект
`marketplaceSource` с `sourceType` и `source`. Для управляемого рынка
`sourceType=local`, а лексические `root` и `source` равны ожидаемой стабильной
точке без предварительного разрешения ссылки.

`plugin list --json` требует оба корневых массива `installed` и `available`,
каждый не более 4096 элементов. Целевой установленный элемент
требует `pluginId`, `name`, `marketplaceName`, `version`, логические
`installed` и `enabled`, объект `source` и объект `marketplaceSource` той же
формы. Должен существовать ровно один установленный и включённый целевой
элемент. В `available` допускается ноль или один целевой элемент; если он
присутствует, его `pluginId`, `version`, рынок и источник обязаны совпасть с
установленным. Второй целевой элемент в любом массиве является конфликтом.
Версия и источник установленного элемента совпадают с `release`, `pluginId`
и неизменяемым деревом активной активации. Добавочные корневые поля и поля
элементов игнорируются. Ответы
изменяющих команд не считаются доказательством: после каждой из них заново
читаются оба списка и разобранный `config.toml`.

## JSONL дочернего процесса

Вывод ограничен 4096 объектами, 16 МиБ и 1 МиБ на строку, обязан быть строгим
UTF-8 JSONL с уникальными ключами и строковым `type`. Пустая строка,
завершающий мусор или частичный объект запрещены. Общие разрешённые события:

```text
thread.started turn.started item.started item.updated item.completed
turn.completed
```

Первая и единственная запись — `thread.started` с непустым `thread_id` до
256 байт. После неё ровно один раз следует `turn.started`; после него идут
элементы. Последняя и единственная запись — `turn.completed`. `turn.failed`,
`error`, неизвестное событие, событие вне этого порядка и ненулевой код
процесса означают неуспех. `turn.completed.usage`, если присутствует, является
строгим объектом неотрицательных целых счётчиков до `2^53-1`; он
диагностический и не заменяет смысловой результат.

Для каждого `item.*` требуется объект `item` размером до 1 МиБ с непустыми
строками `id` до 256 байт и `type` до 64 байт. Один `id` не может сменить тип;
после `item.completed` обновления запрещены. `item.updated` требует
предшествующий `item.started`; `item.completed` также требует его, кроме
`reasoning` и `agent_message`, которые допускают ровно одно непосредственное
завершение. К моменту `turn.completed` каждый начатый элемент обязан быть
завершён. Добавочные описательные поля известного события или элемента
ограниченно разбираются, но игнорируются.

Защитные проекции типов закрыты:

- `agent_message` требует строковый `text` до 1 МиБ;
- `reasoning` допускает только диагностические строки до 1 МиБ и никогда не
  является результатом;
- `command_execution` требует строковую `command` до 64 КиБ, `status` из
  `in_progress`, `completed`, `failed`, необязательные `aggregated_output` до
  4 МиБ и целый `exit_code` в завершённом состоянии;
- `file_change` требует массив изменений до 4096 элементов с абсолютным
  путём внутри карантина и видом `add`, `update`, `delete`; содержимое и
  различия ограничены общим пределом вывода.

Разрешённые типы зависят от роли:

| Роль | Разрешённые типы элемента | Смысловой результат |
|---|---|---|
| пограничный классификатор | `reasoning`, `agent_message` | ровно одно завершённое `agent_message` со строгим объектом оценки |
| читающий субагент | `reasoning`, `agent_message`, `command_execution` | ровно одно последнее завершённое `agent_message` со строгим объектом результата; команды допустимы только в профиле чтения, а изменения файлов запрещены |
| пишущий субагент | `reasoning`, `agent_message`, `command_execution`, `file_change` | ровно одно последнее завершённое `agent_message`; команды и изменения остаются только доказательством карантинной работы |

`mcp_tool_call`, `web_search`, `todo_list`, любой будущий тип и `file_change`
в читающей роли блокируют результат. Расширение списка требует нового выпуска
договора и активационной пробы. Официальная документация перечисляет более
широкую поверхность JSONL, поэтому ограничение ролей является намеренной
защитой, а не предположением о полном наборе Codex:
[неинтерактивный режим Codex](https://developers.openai.com/codex/noninteractive).

Текст единственного итогового `agent_message` разбирается строгим JSON с
запретом повторных ключей и проверяется по именованной схеме роли. Имя схемы и
её `schemaSha256` обязаны совпасть с `SemanticV1` и точным файлом, переданным
через `--output-schema`. Ни JSONL, ни текст сообщения не могут указать другую
схему. Отпечаток смыслового результата строится только после этой проверки.

## Хуки и телеметрическая аттестация

Вход `UserPromptSubmit` и `Stop` ограничен 64 КиБ и требует непустые строки
`hook_event_name`, `session_id`, `turn_id`, `cwd`; `cwd` — существующий
абсолютный каталог. Неизвестное входное поле игнорируется, неизвестное событие
даёт безопасный ответ без умного маршрута.

Выходы событий являются двумя разными закрытыми объектами. Выход
`UserPromptSubmit` допускает только `continue: boolean`, `stopReason: string`,
`suppressOutput: boolean`, `systemMessage: string`, `decision: "block"`,
`reason: string` и `hookSpecificOutput`. Последний разрешён только для
`UserPromptSubmit`, является закрытым объектом, требует
`hookEventName="UserPromptSubmit"` и допускает необязательный
`additionalContext` только строкового типа. Предел строки равен 2048 байтам
её исходного UTF-8-представления включительно; число знаков не используется
как мера длины. Выход `Stop` допускает только
`continue`, `stopReason`, `suppressOutput`, `systemMessage`, `decision`,
`reason` тех же типов и никогда не допускает `hookSpecificOutput`.
`continue` по умолчанию равен `true`, `suppressOutput` — `false`; если
`decision="block"`, требуется `reason.trim()` с хотя бы одним непробельным
знаком. Пустая строка и строка только из пробелов, табуляций или переводов
строки блокируют умный маршрут. Добавочное выходное поле, неверный тип или
`hookSpecificOutput` в `Stop` также блокирует умный маршрут.

Граничные векторы принимают строку из многобайтовых знаков длиной ровно 2048
байт и отклоняют числовое значение и многобайтовую строку длиной 2049 байт.
Последняя содержит меньше 2048 знаков, поэтому проверка по числу знаков вместо
исходных UTF-8-байтов обязана провалить этот вектор.

Одноразовый приёмник принимает только `127.0.0.1`, случайный путь и заголовок,
до 32 запросов по 4 МиБ, только `application/json`. Тело имеет строгую
защитную проекцию OTLP/HTTP JSON:

```text
resourceLogs[]
  .resource.attributes[] = {key,value:AnyValue}
  .scopeLogs[]
    .scope.attributes[] = {key,value:AnyValue}
    .logRecords[]
      .attributes[] = {key,value:AnyValue}
```

Не более 32 `resourceLogs`, 64 `scopeLogs`, 4096 записей и 256 атрибутов на
уровень. Для каждого выбранного ключа `AnyValue` обязан иметь ровно
`stringValue`; иная форма блокирует аттестацию. Неизвестные атрибуты могут
иметь прочие стандартные формы `boolValue`, `intValue`, `doubleValue`,
`bytesValue`, `arrayValue`, `kvlistValue`, но только проверяются по пределам и
не сохраняются. Повтор ключа на одном уровне запрещён. Значения ресурса,
области и записи объединяются без приоритета: повтор на разных уровнях
разрешён только при побайтном равенстве, конфликт блокирует запись.

Из телеметрии извлекаются только поля:

```text
event.name name app.version service.version model reasoning_effort
conversation.id sandbox_policy approval_policy
```

`event.name` и `name`, если присутствуют вместе, обязаны совпасть. Остальные
атрибуты игнорируются и не сохраняются. Требуется хотя бы одна запись с именем
`codex.conversation_starts`; каждая такая запись требует `model`,
`reasoning_effort`, `conversation.id` и хотя бы одно из `app.version`,
`service.version`. Все присутствующие значения версий во всём принятом пакете
обязаны совпасть друг с другом и с нормализованной версией частного снимка.
Модель и уровень совпадают с запросом, а `conversation.id` — с `thread_id`
JSONL. Если
`sandbox_policy` или `approval_policy` присутствуют, они совпадают с запросом.
Сырые тела, подсказка пользователя и неизвестные атрибуты не журналируются.

## Пробы, бюджеты и безопасный отказ

Полная активационная проверка выполняется только на частном снимке:

1. подпись, хеш, версия и платформа;
2. справка и нормативные параметры;
3. встроенный каталог, `initialize`, `configRequirements/read`, `model/list`,
   `hooks/list`;
4. отрицательные пробы прав, песочницы и обязательных отключений;
5. читающий и пишущий запуск в отдельном синтетическом репозитории;
6. JSONL, телеметрия, профиль `arg0-v1` и отсутствие выхода из карантина;
7. запрет опасного принудительного удаления и разрешение безопасного удаления
   принадлежащего пробе файла;
8. добавление, чтение, удаление и повторное добавление синтетического локального
   рынка с тем же именем, но другим источником.

Предел версии или справки — 10 секунд; запроса сервера приложения — 30 секунд;
всей пагинации — 45 секунд; отрицательной пробы — 30 секунд; дочерней
активационной пробы — 120 секунд; всей проверки — 300 секунд. Не более 16 МиБ
от каждого машинного вывода. Внутренний предел ограничивается остатком общего
бюджета. Истечение срока, неоднозначная форма или неполное доказательство
выключают умный режим.

Если свидетельство интерфейса не совпадает со снимком, `codex-smart` запускает
обычный Codex. Если нельзя получить свежее свидетельство учётной среды,
контроллер отклоняет только фактическую попытку узла; построение плана не
запускает такой сбор. Сетевой сбой не блокирует обычный Codex, не разрешает
устаревший список моделей и не вызывает скрытый повтор на другой модели.

## Адаптер временной ссылки `arg0-v1`

Единственный разрешённый профиль временного `argv[0]` имеет форму
`<runtime>/codex-home/tmp/arg0/codex-arg0XXXXXX/ALIAS`, где шесть знаков
`X` принадлежат `[A-Za-z0-9]`, а `ALIAS` является одним из `apply_patch`,
`applypatch`, `codex-execve-wrapper`. Все родительские каталоги принадлежат
текущему пользователю и имеют режим `0700`; `.lock` является частным обычным
файлом с одной жёсткой связью. Конечная цель ссылки обязана совпасть по
устройству, номеру файла и SHA-256 с частным снимком Codex. Любая иная форма
требует нового именованного адаптера и отдельной отрицательной пробы.

## Машинные результаты управления подключаемыми модулями

Команда с `--json` должна завершиться кодом 0 и вывести ровно один строгий
объект. Обязательные проекции текущего договора:

| Команда | Обязательные поля |
|---|---|
| `plugin marketplace add PATH --json` | строковые `marketplaceName`, `installedRoot`, логическое `alreadyAdded` |
| `plugin marketplace remove NAME --json` | строковое `marketplaceName`, `installedRoot` как строка или `null` |
| `plugin add ID --json` | строковые `pluginId`, `name`, `marketplaceName`, `version`, `installedPath`; `authPolicy` из `ON_INSTALL`, `ON_USE` |
| `plugin remove ID --json` | строковые `pluginId`, `name`, `marketplaceName` |
| `plugin marketplace list --json` | массив `marketplaces` |
| `plugin list --json` | массивы `installed` и `available` |

Добавочные поля внешнего объекта разрешены после проверки обязательной
проекции. Мутационный ответ не доказывает итог: после него повторно читаются
оба списка и `config.toml`. Повтор целевой записи, иной источник или неверный
тип обязательного поля дают `REGISTRY_OWNERSHIP_CONFLICT`; посторонние записи
не изменяются.
