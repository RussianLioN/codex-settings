# Проект идемпотентного установщика активации версии 2

## Цель

Перевести `scripts/install_adaptive_subagents.py` со старого изменяемого дерева
и собственного манифеста версии 1 на принятый жизненный цикл активации версии
2. Первый `--apply` должен запустить полноценный контроллер из исходного
дерева, дождаться одновременно публичного `ActivationResolver.READY` и
частного `command.sock`, а затем зарегистрировать стабильный
`marketplace-current` и расширение. Повторное применение с тем же отпечатком
исходников должно быть неизменяющим и после остановки процесса использовать
`ControllerSupervisorV2` для восстановления.

## Выбранная архитектура

Установщик не создаёт и не изменяет lifecycle-манифест. Его публикует только
контроллер через materializer версии 2. Установщик владеет отдельной закрытой
квитанцией `codex-smart-subagents-v2.installer.json` со `schemaVersion=2`,
отпечатком исходников и точными внешними артефактами. Такое разделение не
ломает отпечаток commit receipt жизненного цикла и даёт доказательство
владения ссылками и регистрацией Codex.

Первый запуск и восстановление разделены:

1. На чистом `CODEX_HOME` установщик проверяет конфликты и создаёт только две
   стабильные ссылки в пользовательском каталоге исполняемых файлов. Их цели
   проходят через `GatewayLayout.marketplace_link`, поэтому смена неизменяемой
   активации не требует менять сами ссылки.
2. Установщик напрямую запускает исходный `controller/server.py --serve-v2`
   в новом сеансе процесса и с закрытым окружением. В него передаются только
   разрешённые системные переменные и четыре несекретных параметра:
   `CODEX_HOME`, `CODEX_V2_SOURCE_ROOT`, `CODEX_V2_CODEX_BIN`,
   `CODEX_V2_WRAPPER_PATH`.
3. Установщик ограниченно ждёт два независимых доказательства: публичный
   `ActivationResolver` возвращает `READY`, а защищённая проверка
   `command.sock` подтверждает доступность полноценного контроллера.
4. Только после двойной готовности выполняются штатные команды
   `codex plugin marketplace add <marketplace-current>` и
   `codex plugin add codex-smart-subagents@codex-settings-adaptive`.
5. После повторной проверки точных регистраций атомарно публикуется закрытая
   квитанция установщика.
6. Повторный `--apply` требует совпадения квитанции, `sourceDigest`, ссылок,
   lifecycle-активации и регистраций. Он не запускает исходный bootstrap, а
   вызывает супервизор установленной активации. Полная готовность возвращает
   `unchanged`; любое несовпадение закрывает операцию без ремонта по догадке.

## Квитанция установщика

Квитанция находится рядом с lifecycle-манифестом, но имеет отдельное имя и
отдельную блокировку:

- `install-manifests/codex-smart-subagents-v2.installer.json`, режим `0600`;
- `install-manifests/codex-smart-subagents-v2.installer.lock`, режим `0600`.

Закрытый объект содержит ровно:

- `schemaVersion=2` и `kind=codex-smart-installer-receipt/v2`;
- `sourceDigest`, `installationId`, `activationId`;
- канонические `codexHome`, `codexBinary` и `marketplacePath`;
- две точные пары `path`/`target` для оболочки и администратора;
- точные идентификаторы рынка и расширения;
- `extensions={}`.

Квитанция не содержит исходный корень, значения `CODEX_V2_*`, окружение,
секреты или телеметрию. Она проверяется по закрытой форме, владельцу,
обычному файлу, одной жёсткой ссылке и режиму `0600`.

## Отпечаток входов установки

`sourceDigest` вычисляется детерминированно по всем входам, которые влияют на
активацию: дереву расширения без кэшей и байткода, описанию рынка, основному
каталогу, нормативным векторам политики, схемам времени выполнения, а также
лексическому пути и содержимому выбранного исполняемого файла Codex. Поэтому
обновление Codex по прежнему пути не маскируется как неизменный повтор. Старый
`codex-highfd` не входит в отпечаток и не устанавливается этим путём.

## Диагностика

`doctor` остаётся только читающим и всегда возвращает одно из трёх состояний:

- `ORDINARY`: публичное доказательство активации не открылось;
- `HEALTH_ONLY`: публичный `ActivationResolver` готов, но `command.sock` не
  доказан;
- `FULL_READY`: оба доказательства готовы.

Поле `ok` истинно только для `FULL_READY` при одновременно совпавших
квитанции, стабильных ссылках и регистрациях. Таким образом
`HEALTH_ONLY` никогда не считается готовой установкой. Повреждение или
неполнота внешних артефактов добавляется в `problems`, но не подменяет
фактическое состояние контроллера четвёртым неоговорённым статусом.

## Безопасный откат сбоя

Установка ведёт локальный перечень только тех артефактов, которые создала
данная попытка. При ошибке действия компенсируются в обратном порядке:

1. удалить расширение, только если попытка его добавила и текущая регистрация
   всё ещё совпадает с точным рынком;
2. удалить рынок, только если попытка его добавила и текущий источник всё ещё
   равен `marketplace-current`;
3. завершить только непосредственно запущенный дочерний процесс по сохранённому
   handle и ограниченно дождаться его остановки;
4. удалить принятую активацию через узкий публичный cleanup API, только если
   совпадают `installationId`, `activationId`, commit receipt, идентичность
   базы и доказана остановка контроллера;
5. удалить только созданные попыткой ссылки, если их лексические цели не
   изменились;
6. удалить квитанцию установщика, только если она была создана этой попыткой
   и её содержимое совпадает.

Cleanup API удаляет только доказанные объекты жизненного цикла и пустые
каталоги. Изменённый, неизвестный или чужой объект не удаляется; откат
возвращает отдельную ошибку с перечнем оставшихся артефактов. Сбой отката не
маскирует первоначальную ошибку.

## Закрытое окружение

Первичный процесс не наследует `PYTHONPATH`, токены, прокси, ключи или
переменные умного режима. Все три `CODEX_V2_*` обязательны для первичного
запуска, но используются только контроллером при bootstrap. Дочерняя модель
строит окружение из собственного белого списка с `inherit=none`, поэтому
эти значения не попадают в процесс модели. Квитанция, результат установки и
телеметрические атрибуты также не содержат их значений.

## Совместимость интерфейса

- Без `--apply` сохраняется просмотр действий без изменений файлов и
  регистраций.
- `--apply`, `--doctor`, `--smoke` и `--json` сохраняются.
- Установщик не вызывает обновление Codex, не меняет настройки модели и не
  управляет сетями операционной системы.
- Пользовательский `config.toml` не копируется и не восстанавливается самим
  установщиком: изменение выполняют только штатные команды регистрации
  Codex, а компенсация — их штатные команды удаления.
- Старое изменяемое `owned_root/marketplace`, schema 1, резервные копии
  конфигурации и `codex-highfd` не создаются новым применяемым путём.

## Проверка

Модульные проверки подменяют запуск контроллера, публичный resolver,
`command.sock` и супервизор, чтобы детерминированно доказать порядок и
закрытые ветви. Отдельные проверки используют поддельный Codex для точных
регистраций и отказов компенсации. Проверка cleanup API строит настоящую
активацию версии 2 и доказывает удаление только после остановки владельца,
отказ при живом владельце и сохранение изменённого либо чужого объекта.
