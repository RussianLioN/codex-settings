# Полный доступ Codex

[Вернуться к центральному каталогу](../../README.md).

## Статус и предупреждение

Это операторский рецепт, а не описание текущей внешней конфигурации. Перед
каждым применением путь, содержимое, ограничения и более приоритетные
настройки проверяются заново. Репозиторий не подтверждает, что текущий
пользовательский `config.toml` уже содержит описанные значения.

Повторно проверенный 23 июля 2026 года снимок интерфейса
`codex-cli 0.145.0` объявляет
параметры `--profile`, `--config`, `--sandbox`, `--ask-for-approval` и
`--strict-config`. Поведение следующей версии нужно проверять повторно.

Полный доступ задаётся двумя ключами верхнего уровня:

```toml
approval_policy = "never"
sandbox_mode = "danger-full-access"
```

Это не означает, что:

- управляемая политика разрешает такие значения;
- хуки и внешние ограничения отключены;
- уже работающая сессия перечитала файл;
- дочерние процессы адаптивного контроллера наследуют полный доступ;
- любая команда обязательно завершится успешно.

## 1. Определить фактический файл

```bash
CODEX_DIR=${CODEX_HOME:-"$HOME/.codex"}
CONFIG="$CODEX_DIR/config.toml"

printf 'CODEX_DIR=%s\nCONFIG=%s\n' "$CODEX_DIR" "$CONFIG"
if [[ -e "$CONFIG" ]]; then
  stat -f 'owner=%Su mode=%Sp size=%z modified=%Sm' "$CONFIG"
  shasum -a 256 "$CONFIG"
else
  printf 'config отсутствует\n'
fi
```

Не выводите всё содержимое пользовательской конфигурации в общий журнал:
файл может содержать пути и настройки подключений. Проверьте владельца, права,
размер, время изменения и отпечаток.

Перед изменением также проверьте:

- `/etc/codex/requirements.toml` и другие управляемые требования;
- проектную `.codex/config.toml`;
- выбранный профиль;
- псевдонимы и оболочки запуска;
- явные `--config`, `--sandbox` и `--ask-for-approval`.

Если управляемая политика запрещает полный доступ, пользовательский файл не
должен использоваться для её обхода.

## 2. Создать резервную копию

Непосредственно перед изменением заново проверьте отпечаток файла. Затем:

```bash
umask 077
mkdir -p "$CODEX_DIR/backups"
STAMP=$(date -u +%Y%m%d-%H%M%S)

if [[ -f "$CONFIG" ]]; then
  BACKUP="$CODEX_DIR/backups/config.toml.$STAMP.bak"
  cp -p -- "$CONFIG" "$BACKUP"
  printf 'backup=%s\n' "$BACKUP"
else
  BACKUP=
  mkdir -p "$CODEX_DIR"
  : > "$CONFIG"
  chmod 600 "$CONFIG"
  printf 'создан новый %s\n' "$CONFIG"
fi
```

Если исходного файла не было, отсутствие резервной копии нужно зафиксировать
отдельно: откат будет означать удаление только созданного пустого или
управляемого файла после проверки его текущего содержимого.

## 3. Изменить только два ключа

Откройте именно значение переменной `CONFIG` в редакторе. Добавьте либо
замените ровно две строки до первой таблицы TOML:

```toml
approval_policy = "never"
sandbox_mode = "danger-full-access"
```

Требования к изменению:

- ключи должны находиться на верхнем уровне, а не внутри `[notice]`,
  `[desktop]`, `[features]`, `[projects.*]` или другой таблицы;
- не должно остаться дубликатов этих ключей на верхнем уровне;
- не менять модель, расширения, MCP, доверие проектов, предупреждения и
  остальные параметры;
- не смешивать это изменение с отдельным профилем
  `full-access.config.toml`;
- не подменять явные ключи опасным псевдонимом `--yolo`, который отключает
  подтверждения и песочницу только для конкретного запуска.

## 4. Проверить синтаксис и расположение ключей

```bash
CONFIG="$CONFIG" python3 - <<'PY'
import os
import pathlib
import tomllib

path = pathlib.Path(os.environ["CONFIG"])
data = tomllib.loads(path.read_text(encoding="utf-8"))
assert data.get("approval_policy") == "never", data.get("approval_policy")
assert data.get("sandbox_mode") == "danger-full-access", data.get("sandbox_mode")
print("config.toml: ok")
PY

codex --strict-config --version
```

Разбор TOML и `--version` подтверждают синтаксис, но не эффективные права уже
работающей сессии. Запустите новую интерактивную сессию без профиля и явных
переопределений, затем проверьте режим через `/status`.

Отдельно убедитесь, что безопасное явное переопределение продолжает иметь
приоритет:

```bash
codex --sandbox read-only --ask-for-approval on-request
```

Пробную запись выполняйте только во временном каталоге вне рабочего
репозитория. Удаляйте только файл, созданный этой проверкой.

## 5. Откат

Перед восстановлением снова зафиксируйте отпечаток текущего файла и сравните
его с состоянием сразу после изменения. Не перезаписывайте более новые
внешние изменения вслепую.

Если резервная копия существует и текущие изменения понятны:

```bash
cp -p -- "$BACKUP" "$CONFIG"
```

Если файла до изменения не было, удаление допустимо только после доказательства,
что он всё ещё содержит исключительно созданные в этой процедуре значения и
не получил более новых пользовательских изменений.

После отката повторите разбор TOML, `codex --strict-config --version` и
проверку `/status` в новой сессии.

## Связь с адаптивными субагентами

- полный доступ относится к корневой обычной сессии;
- установщик адаптивного режима не меняет эти ключи;
- дочерние процессы запускаются с `--ignore-user-config` и собственными
  профилями прав;
- полный доступ корневого координатора не является границей безопасности
  дочерних процессов.

Подробности: [адаптивные субагенты](../../plugins/codex-smart-subagents/README.md)
и [архитектурное решение](../decisions/001-adaptive-subagents-external-controller.md).
