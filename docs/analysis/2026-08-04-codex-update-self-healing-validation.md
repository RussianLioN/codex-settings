# Живая проверка самовосстановления после обновления Codex

Дата: 2026-08-04.

Статус: завершено успешно. Выполнены два последовательных применения,
диагностика установленного состояния и обычный интерактивный запуск `codex`
из трёх каталогов.

## Проверяемое утверждение

После замены системного Codex и удаления физического каталога прежней версии
сохранённая активация доказывается на неизменяемом снимке. Установщик принимает
новый совместимый исполняемый файл ровно одной операцией, повторное применение
не создаёт новую активацию, а обычная пользовательская команда `codex`
работает независимо от текущего каталога.

## Причина прежнего отказа

После обновления системного Codex с `0.145.0` до `0.146.0` Homebrew удалил
каталог прежней версии. Принятая активация сохранила проверенный снимок, но
шлюз ошибочно требовал, чтобы текущая активная версия и независимая аварийная
капсула указывали на один и тот же исходный файл и снимок. После принятия
нового системного Codex это условие становилось ложным, поэтому обычная команда
останавливалась с сообщением `SOURCE_CHANGED`.

Исправление разделило два назначения:

1. аварийная капсула отдельно доказывает, что обычный Codex можно запустить
   даже при повреждении управляемой активации;
2. активный манифест отдельно привязывает принятую версию к её собственному
   исходному файлу и неизменяемому снимку;
3. восстановление уже зафиксированного обновления запускает код контроллера
   из текущего установщика, но использует принятую политику, базу состояния и
   снимок активной активации.

## Диагностика установленного состояния

Команда

```bash
python3 scripts/install_adaptive_subagents.py --doctor --json
```

вернула одновременно внешний статус `READY` и внутреннюю готовность
`FULL_READY`, без проблем. Административная команда

```bash
~/.local/bin/codex-smart-subagents-admin status
```

подтвердила живой контроллер в состоянии `ACCEPTING`, поколение управления
`4` и ту же активную активацию.

Обе команды `codex --version` и `codex-native --version` показали
`codex-cli 0.146.0`. Это подтверждает, что управляемая и нативная точки входа
видят текущий выпуск, но не подменяют друг друга.

## Запуск из разных каталогов

Обычная команда `codex` была запущена в новых интерактивных оболочках из:

- `/Users/s060874gmail.com/coding/projects/codex-settings`;
- `/Users/s060874gmail.com/coding/projects/datacanvas`;
- `/Users/s060874gmail.com`.

Во всех трёх случаях открылся штатный интерфейс Codex `0.146.0`, сообщение
`SOURCE_CHANGED` отсутствовало. В заголовке каждого запуска наблюдалась
корневая пара `gpt-5.6-sol` и уровень рассуждений `medium`. Все три
испытательных процесса затем были штатно завершены.

Домашний каталог при первом запуске показал обычный запрос доверия Codex к
каталогу. Это штатная проверка самого Codex, не отказ адаптивного запуска;
после неё открылся тот же интерфейс.

Проверка `type -a codex` во всех трёх каталогах показала один и тот же
пользовательский псевдоним через `~/.local/bin/codex-highfd`, а
`type -a codex-native` — тот же управляемый нативный обход. Следовательно,
работа не привязана к `datacanvas` или к корню этого репозитория: она
определяется пользовательской настройкой интерактивной оболочки.

Дополнительная проверка из `/private/tmp`, то есть вне любого пользовательского
репозитория, получила те же псевдонимы и версии `codex-cli 0.146.0` для
`codex` и `codex-native`. Команда завершилась с кодом `0`.

## Автоматические проверки

Целевые проверки шлюза активации охватили независимость аварийной капсулы,
обязательную физическую доступность её исполняемого файла и совпадение снимка
активного манифеста с личностью активации. Проверка входной точки установщика
подтвердила восстановление уже зафиксированного обновления через текущий код
установщика. Отдельная проверка машинной схемы квитанции выполнена в
закреплённом окружении зависимостей.

Итоговый `make quality` завершился с кодом `0`: прошли контракты, проверка
навигации, `1940` модульных испытаний и компиляция. Ошибок не было; одна
неприменимая в текущем окружении проверка штатно пропущена. Проверка
`git diff --check` также завершилась без замечаний.

## Граница доказанного результата

Проверка доказывает глобальную точку входа для интерактивной оболочки `zsh`
текущего пользователя и трёх разных рабочих каталогов. Она не утверждает, что
псевдоним оболочки действует в оболочке, которая намеренно не читает
пользовательские файлы настройки. Такая оболочка может использовать прямую
системную команду из `PATH`, что является отдельным способом запуска.
