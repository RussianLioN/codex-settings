# Автономная работа Codex

[Вернуться к центральному каталогу](../../README.md).

## Статус и границы

Это актуальное руководство по уже развёрнутому пользовательскому процессу.
Репозиторий содержит проверяющий сценарий, локальную очередь, политику хуков,
откат и схему задания, но не содержит установщика или шаблонов всех
пользовательских профилей и ролей. Готовность конкретного внешнего профиля
подтверждается проверкой, а не наличием этого документа.

Повторная проверка 23 июля 2026 года показала локальный стабильный
`codex-cli 0.145.0`, совпадающий с текущим стабильным выпуском. Адаптивный
путь версии 2 допускает проверенные версии `0.144.4`, `0.144.5`, `0.144.6` и `0.145.0`,
а затем выполняет пробы фактических возможностей и доступных текущей учётной
записи пар «модель — уровень рассуждения». Неизвестный будущий выпуск
безопасно запускается в обычном режиме до отдельной проверки. Историческая
реализация
версии 0.1.0 по-прежнему относится только к Codex 0.144.4 и не должна
использоваться вместо нового пути.

Полный `scripts/validate_autonomous_workflow.py` не является чисто читающей
проверкой. Он всегда обращается к профилю в `~/.codex`, не учитывает
альтернативный `CODEX_HOME`, запускает настоящее соединение MCP и вызывает
хуки, которые могут дописать `~/.codex/audit/hooks.jsonl`.

После согласования новой точки входа обычная команда `codex` становится
управляемым интерактивным входом адаптивных субагентов. Для нативной работы и
прежних ручных профилей используются отдельные псевдонимы; это разделяет
доказуемую маршрутизацию версии 2 и старые автономные волны.

## Выбор режима

| Потребность | Режим |
|---|---|
| Обычная инженерная работа с заранее выбранными моделью и правами | Профиль `standard`, `safe-readonly` или другой ручной профиль |
| Параллельное чтение, исследование и независимые проверки | Интерактивная волна субагентов после проверки файловых дескрипторов |
| Один изолированный пакетный запуск из доверенной спецификации | Локальная очередь и профиль `batch-workers` |
| Выбор Luna, Terra или Sol и уровня рассуждения для каждой подзадачи | [Адаптивные субагенты](../../plugins/codex-smart-subagents/README.md#как-проходит-умный-ход) |
| Ручная корневая сессия без ограничений | [Полный доступ](full-access.md); не использовать для массового запуска субагентов |

Обычный автономный процесс не выбирает модель динамически для каждой
подзадачи. Модель, уровень рассуждения и права заранее определяются профилем.
Адаптивный контроллер дополняет этот процесс, но не заменяет ручные профили,
правила волн и локальную очередь.

## Проверяемые профили

Внешние файлы могут располагаться в выбранном `CODEX_HOME` и не являются
отслеживаемыми файлами этого репозитория. Однако текущий валидатор жёстко
проверяет только `~/.codex`; при альтернативном `CODEX_HOME` результат нельзя
считать подтверждением выбранного каталога. Для стандартного расположения
валидатор ожидает:

| Профиль | Модель | Рассуждение | Права | Потоки |
|---|---|---|---|---:|
| `small` | `gpt-5.4-mini` | `medium` | запись в рабочей области, подтверждение по запросу | 2 |
| `standard` | `gpt-5.5` | `high` | запись в рабочей области, подтверждение по запросу | 4 |
| `deep-review` | `gpt-5.5` | `xhigh` | только чтение, подтверждение по запросу | 4 |
| `safe-readonly` | `gpt-5.5` | `high` | только чтение, без подтверждений | 2 |
| `wide-readers` | `gpt-5.4-mini` | `medium` | только чтение, без подтверждений | 8 |
| `wide-readers-16` | `gpt-5.4-mini` | `medium` | только чтение, без подтверждений | 16 |
| `batch-workers` | `gpt-5.4-mini` | `medium` | запись в рабочей области, без подтверждений | 1 |
| `full-access` | `gpt-5.5` | `xhigh` | полный доступ, без подтверждений | 4 |

Базовая конфигурация должна иметь `agents.max_threads = 20`,
`agents.max_depth = 1` и `agents.job_max_runtime_seconds = 1800`. Потолок
профиля не является рекомендуемым размером волны: обычная живая волна
ограничена шестью субагентами. Профиль `wide-readers-16` предназначен только
для отдельного испытания и не имеет псевдонима оболочки.

После применения `scripts/reconcile_codex_entrypoint.py` ожидаются ровно семь
пользовательских псевдонимов:

| Псевдоним | Назначение |
|---|---|
| `codex` | Новый управляемый интерактивный запуск: включает два признака, проходит через `codex-highfd`, затем `codex-smart` и контроллер версии 2 |
| `codex-native` | Прямой нативный Codex без контроллера и без умной маршрутизации |
| `codexs` | Нативный профиль `standard` |
| `codexro` | Нативный профиль `safe-readonly` |
| `codexwide` | Нативный профиль `wide-readers` |
| `codexfa` | Нативный профиль `full-access` |
| `codexfd` | Только диагностика файловых дескрипторов |

`codex help` и `codex update` выполняются нативно без подготовки контроллера.
`codex -- help` и `codex -- update` являются текстом пользовательского запроса
и остаются в управляемом пути. Если обычный управляемый запуск не может
доказать умный контур, он всё равно запускает основной Codex с исходными
аргументами, очищает недоказанное умное окружение и не требует перехода на
`codex-native`. Закрытый отказ с кодом 69 сохраняется только для явно строгих
внутренних административных операций. `codex-native` и `codex-smart` остаются
диагностическими командами, но не являются рекомендуемым повседневным входом.

## Предварительная проверка

Из корня репозитория:

```bash
codex --version
python3 scripts/validate_autonomous_workflow.py
~/.local/bin/codex-highfd --self-test
CODEX_SMART_ENABLED=1 CODEX_SMART_REQUIRED=1 ~/.local/bin/codex-highfd --self-test
CODEX_SMART_ENABLED=0 CODEX_SMART_REQUIRED=0 ~/.local/bin/codex-highfd --self-test
~/.local/bin/codex-highfd --fd-doctor --wave-size 6
```

Первую команду нужно сопоставить с профилями и установленными расширениями.
Полный валидатор запускают только после принятия его внешних побочных действий.
Для проверки без обращения ко всему пользовательскому профилю сначала
достаточно проверить обе ветви `codex-highfd --self-test` и файловые
дескрипторы. В управляемой ветви должны быть видны `smart_enabled=1` и
`smart_required=1`; в нативной ветви — `0` и `0`.

Результат проверки файловых дескрипторов:

- код `0`, `status=OK` — запуск разрешён;
- код `1`, `status=WARN` — разрешена только обычная волна не более 6;
- код `2`, `status=BLOCK` — новые субагенты не запускаются;
- размер больше 6 требует мягкого предела не ниже 4096 и отдельного испытания;
- сценарий принимает размер от 1 до 20, но это не разрешение использовать
  максимальное значение в обычной работе.

При `Too many open files`, `EMFILE`, устаревших процессах `node_repl` или
неразрешимом пути MCP новые субагенты не запускаются до устранения причины.

## Интерактивные волны

Корневой диалог всегда остаётся координатором: он сохраняет цель, принимает
решения, объединяет результаты и отвечает за финальную проверку. Рекомендуемый
порядок:

1. читающие репозиторий и документацию;
2. проверяющие и запускающие проверки;
3. авторы только с непересекающимися областями записи;
4. независимая итоговая проверка.

Обязательные правила:

- перед волной закрыть завершённые и устаревшие потоки;
- не запускать более 6 обычных субагентов одновременно;
- оставлять `agents.max_depth = 1`;
- перед ожиданием выполнять доступную полезную работу;
- обычное ожидание выполнять по 60 секунд;
- после двух пустых ожиданий один раз проверить список агентов;
- после третьего пустого ожидания проверить процессы, журналы и Git;
- не прерывать агента только из-за истечения времени ожидания;
- для длительной задачи запрашивать этапный отчёт каждые 2–3 минуты;
- закрывать завершённого агента сразу после получения результата;
- не передавать субагенту решения о публикации, слиянии или выпуске.

Читающие агенты могут использовать основную рабочую копию. Любая параллельная
запись выполняется в отдельной рабочей копии Git, принадлежащей ровно одному
заданию и одной попытке.

## Локальная очередь заданий

Очередь принимает только доверенные спецификации: значения
`validation_commands` выполняются через командную оболочку. Обязательные поля
описаны в [схеме задания](../../schemas/codex-batch-task.schema.json).

Используйте явные пути к базе, рабочим копиям и артефактам вне отслеживаемой
рабочей копии:

```bash
QUEUE_ROOT=/абсолютный/приватный/каталог

python3 scripts/codex_batch_queue.py \
  --db "$QUEUE_ROOT/tasks.sqlite3" \
  init-db

python3 scripts/codex_batch_queue.py \
  --db "$QUEUE_ROOT/tasks.sqlite3" \
  enqueue /путь/к/заданию.json

python3 scripts/codex_batch_queue.py \
  --db "$QUEUE_ROOT/tasks.sqlite3" \
  list

python3 scripts/codex_batch_queue.py \
  --db "$QUEUE_ROOT/tasks.sqlite3" \
  show ИДЕНТИФИКАТОР

python3 scripts/codex_batch_queue.py \
  --db "$QUEUE_ROOT/tasks.sqlite3" \
  run-once \
  --attempt-root "$QUEUE_ROOT/worktrees" \
  --artifact-root "$QUEUE_ROOT/artifacts"
```

Один `run-once`:

1. выбирает одно задание в состоянии `queued`;
2. создаёт отдельную ветку и рабочую копию;
3. запускает `codex exec --profile batch-workers --json`;
4. последовательно выполняет команды проверки;
5. сохраняет запрос, команду запуска, события, ошибки, итог, журнал проверки,
   состояние Git и двоичную разницу;
6. переводит задание в `succeeded`, `failed` или `retryable`.

Это однократный локальный исполнитель, а не полный диспетчер:

- просроченные аренды автоматически не возвращаются в очередь;
- состояние `retryable` автоматически не запускается повторно;
- отдельного надзирателя публикации нет;
- рабочая копия и ветка автоматически не удаляются;
- публикация и слияние не выполняются;
- `validation_profile` и `output_schema` передаются в запрос, но результат не
  проверяется против них машинно;
- схема JSON описывает контракт, но исполнитель проверяет только обязательные
  поля и тип списка команд проверки.

Параметр `run-once --dry-run` изменяет состояние. Он арендует задание,
записывает попытку в базу, создаёт каталог артефактов, сохраняет запрос и
помечает попытку успешной. Для пробного просмотра используйте отдельную копию
базы и отдельный каталог артефактов.

Значения путей по умолчанию создают `.codex-batch` относительно текущего
каталога. Этот путь не исключён в `.gitignore`, поэтому в рабочих
репозиториях следует всегда задавать внешние абсолютные пути.

## Хуки и границы защиты

Установленная политика:

- разрешает только утверждённые роли;
- блокирует известные разрушительные команды;
- блокирует `git push` для распознанного автономного агента;
- блокирует `gh pr merge` для всех сессий;
- проверяет цели `apply_patch`;
- блокирует известные записи за пределы рабочей копии и обращения к
  защищённым каталогам;
- эвристически блокирует изменяющие внешнее состояние инструменты MCP и
  подключений;
- записывает решения в журнал.

Хук не является границей операционной системы и не гарантирует распознавание
любого возможного способа записи. Безопасность дополнительно обеспечивают
профиль прав, отдельная рабочая копия, узкая область записи и независимая
проверка.

## Откат старого автономного процесса

Сначала просмотреть действия:

```bash
python3 scripts/codex_autonomous_rollback.py \
  --backup /путь/к/резервной-копии
```

После проверки применить:

```bash
python3 scripts/codex_autonomous_rollback.py \
  --backup /путь/к/резервной-копии \
  --apply
```

Сценарий жёстко работает с `~/.codex` и не учитывает альтернативный
`CODEX_HOME`. Он восстанавливает сохранённую конфигурацию, псевдонимы,
политику, навыки и кеши. Перед применением нужно проверить, не появились ли
после резервной копии новые пользовательские изменения. Закрытие агентов и
удаление рабочих копий остаётся ручным.

Это не откат адаптивных субагентов. Для них используется отдельная процедура
из [операционной инструкции](../runbooks/adaptive-subagents-v2-operations.md#8-жизненный-цикл-установки).
