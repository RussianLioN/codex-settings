# Корневое исправление запуска и возобновления умного Codex

## Цель

Обычные `codex` и `codex resume --last` всегда должны запускать основной
Codex. Недоказанный умный маршрут должен становиться недоступным, но отказ
каталога моделей, аренды, обработчика или управляющего процесса не должен
останавливать пользовательский запрос и требовать ручного `codex-native`.

## Подтверждённые причины

1. Выбор координатора вычисляется один раз при старте управляющего процесса.
   Временный тайм-аут каталога превращается в долговечный
   `COORDINATOR_ACCOUNT_CATALOG_UNAVAILABLE`.
2. `CODEX_SMART_LAUNCH_KIND=resume` сохраняется на весь срок процесса. Каждый
   `UserPromptSubmit` повторно привязывает старый маршрут.
3. Аренда считает `baseSha` и отпечаток рабочей копии неизменной личностью
   проекта. Обычная правка или коммит закономерно ломают следующий запрос.
4. После прерывания `BOUND` освобождается только узкой веткой `Stop`, поэтому
   старая привязка может блокировать все последующие ходы.
5. `status` и `doctor` способны сообщить `READY`, хотя сохранённый выбор
   координатора недоступен.

## Неизменяемые правила

- Ошибка умной надстройки не возвращает `continue: false` из `SessionStart`
  или `UserPromptSubmit` и не завершает обычный запуск кодом 69.
- При полной готовности действует умная маршрутизация.
- При недоступном каталоге Codex запускается без принудительной модели и
  уровня рассуждений; сохранённая модель возобновляемого сеанса сохраняется.
- При недоступной активации автоматически запускается проверенный настоящий
  исполняемый файл Codex с очищенным окружением.
- Старый недоказанный маршрут не присоединяется и не изменяется в базе.
- `codex-native` остаётся только диагностическим средством.

## Task 1: Доступный запуск и самовосстанавливающийся каталог

- Сначала добавить RED-проверки шлюза: временно недоступный каталог не завершает обычные
  `codex` и `codex resume` кодом 69 и не требует `codex-native`.
- Убрать `CODEX_SMART_REQUIRED=1` из стандартного псевдонима.
- Для обычного интерактивного запуска игнорировать устаревшее требование
  строгого умного режима; строгий отказ оставить только внутренним
  административным операциям.
- При недоступности выбора координатора не добавлять `--model` и
  `model_reasoning_effort`, но запускать управляемый ограниченный сеанс.
- При недоступности активации автоматически выполнять настоящий Codex с
  исходными аргументами и очищенным умным окружением.
- Оставить быструю начальную проверку, не задерживающую запуск.
- После временного отказа запускать один фоновый повтор со сроком 20 секунд.
- Последующие интервалы: 5, 30, 120 и максимум 300 секунд.
- Успешный результат атомарно публиковать в health без перезапуска процесса.
- После успеха выполнять контрольную проверку раз в пять минут.
- Завершение управляющего процесса обязано останавливать и присоединять
  фоновый исполнитель без утечки процессов и файловых дескрипторов.

## Task 2: Согласование возобновления без остановки основного запроса

- Сначала добавить RED-проверки обработчиков: ошибки Git, аренды,
  контроллера и совместимости возвращают продолжение основного запроса.
- Воспроизвести второй и последующие запросы после правки, коммита,
  прерывания при `BOUND`, сбоя `Stop` и временно занятой блокировки.
- Перевести аренду на версию 3, разделив стабильную личность проекта
  (`repoRoot`, отпечаток совместимости) и изменяемый снимок (`baseSha`,
  отпечаток рабочей копии).
- Использовать состояния `PREPARED`, `CLAIMING`, `BOUND`,
  `PENDING_NEXT_TURN`, `ACKNOWLEDGED`, `DETACHED`.
- `SessionStart` только регистрирует владельца и готовит кандидата.
- `UserPromptSubmit` согласует присоединение по состоянию аренды, а не по
  постоянной переменной окружения.
- Изменившийся снимок переводит старый маршрут в `DETACHED`, после чего
  текущий запрос получает обычное новое планирование.
- `BOUND` старого хода того же владельца и неизменившегося снимка можно
  безопасно перепривязать на границе следующего запроса без зависимости от
  `Stop`.
- Для аварийной устойчивости использовать двухфазный `CLAIMING` с
  одноразовым идентификатором, который сохраняется и в контексте хода.
- Старую аренду версии 2 переносить только при полном совпадении; любое
  несовпадение создаёт исправную аренду без присоединения и не блокирует
  основной запрос.
- Проверить, что исчерпание доступных нитей запрещает новый маршрут, но не
  основной запрос.

## Task 3: Диагностика, установщик и документация

- `READY` означает полностью доступную умную маршрутизацию.
- `DEGRADED` означает доступный основной Codex при временно ограниченной
  умной части.
- Выводить безопасный код причины, состояние выбора координатора, время
  последней успешной проверки и следующей попытки.
- Обновить центральную навигацию, руководство эксплуатации, диаграмму и
  инструкцию `codex resume --last`.

## Task 4: Приёмка и публикация

- Выполнить целевые, договорные, документационные и полные проверки проекта.
- Применить глобальную установку дважды: первый результат `upgraded`, второй
  `unchanged`.
- В двух временных Git-репозиториях и каталоге без Git проверить новый
  запуск, несколько запросов, правку, коммит, прерывание, выход и
  `codex resume --last`.
- Выполнить не менее десяти последовательных циклов запуска и возобновления.
- Не признавать исправление готовым при наличии хотя бы одного сообщения
  `SessionStart hook (stopped)`, `UserPromptSubmit hook (stopped)`, просьбы
  использовать `codex-native` или кода 69 у обычной команды.
- После приёмки сделать коммиты, отправить ветку, открыть запрос на слияние,
  провести независимое ревью, дождаться проверок, слить и удалить только
  принадлежащие задаче ветку и дополнительную рабочую копию.
